ADR-37: measure the SHIPPED model (nobody ever had) -- and find it at chance

metrics.json stays unwritten, for a reason I had not established before:
ai/src/evaluate.py feeds its classification metrics to a Keras .keras model
it loads itself; the .tflite it accepts is used only for latency. So
metrics.json describes a model this repo would have to train, and writing it
from any other model into the shipped card's metricsRef would be a false
claim about the artifact users install.

But that exposed the real gap: the accuracy of the model that actually ships
had never been measured here -- the only number available was the model
team's 55.9%.

New tool tool/evaluate_shipped_model.py measures it with the repo's own
frozen chain (augment_mod.feature_tensor, the same call evaluate.py's
predict_split makes) over ai/data/splits:

  test_public    78/468  = 16.67%
  test_mobile    24/144  = 16.67%   Wilson 95% CI [11.46%, 23.60%]
  chance for 6 balanced classes = 16.67%

Diagnostic (117 clips, class-strided): mean predicted probability is
cabbage 0.485 / chips 0.309 / noodles 0.150 but gummies 0.019, carrot 0.029,
drink 0.009 -- those three are NEVER argmax. A zero-input control returns a
near-flat distribution, so the model does respond to input; the output mass
is simply collapsed onto 3 of 6 classes.

I got this wrong first: v1 used features.mel_of_file, which is a DIFFERENT
function from the one the repo evaluates with. Re-running through
feature_tensor gives the same 16.67%, so it is not a harness artifact. Both
the mistake and the check are recorded in ADR-37.

verify_artifacts.py gains gate 11 (ACD-ART-006): the shipped-model report
must exist and name the sha256 currently in app/assets/models/. Measured
negative control: corrupting that sha256 fails the gate.
