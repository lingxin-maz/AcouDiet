EatSense 产品概念主视觉：以手机麦克风为入口，通过声学AI感知实现无感饮食记录

1. 项目概述

在全民健康意识持续升级的时代，饮食管理已成为当代青年日常健康管控的核心环节。然而，当下主流健康管理应用均依赖用户手动录入、拍照识别、扫码填写等主动式记录方式，操作流程繁琐、使用门槛高，绝大多数用户难以长期坚持，导致饮食数据断层、健康分析失效，行业普遍存在"有需求、无留存、难坚持"的核心痛点。

针对传统饮食记录模式的高操作成本、低用户留存与隐私泄露风险等行业难题，EatSense 创新性提出端侧AI声学无感饮食识别方案，打造全新一代智能饮食健康管理助手。项目通过手机麦克风采集用户进食过程中产生的咀嚼声、吞咽声等声学信号，经过音频预处理、Mel 频谱特征提取与轻量化深度学习模型推理，对典型食物类别和饮食行为进行实时识别，并自动生成饮食日志与个性化健康建议。

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  核心定位：EatSense 不是单纯的"AI食物分类器"，而是一款以声学感知为入口、以端侧AI为技术基础、以无感记录为核心体验的智能饮食健康管理助手。项目愿景是让记录饮食从"动手"变成"无感"。
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

在数据处理层面，核心 AI 推理全程在移动端本地完成，原始音频默认不上传服务器，从架构层面降低用户隐私泄露风险。系统在识别食物后，可自动生成饮食日志，并结合进食时长、咀嚼节律、进食速度、零食频率等多维度行为数据，对用户近期饮食习惯进行深度分析，进一步生成个性化的健康饮食建议。

项目初期以可演示移动端原型为核心目标，在有限开发周期内完成"声音采集 → AI识别 → 自动记录 → 健康分析"的完整产品闭环，验证声学感知在无感饮食管理场景下的技术可行性与产品价值。

2. 项目背景与痛点分析

2.1 饮食健康管理需求持续增长

随着生活节奏加快，饮食结构不规律、零食摄入频繁、进食速度过快等问题逐渐成为年轻群体常见的生活习惯问题。《中国居民营养与慢性病状况报告》显示，我国成年居民超重肥胖率已超过50%，不合理膳食是导致慢性病的重要危险因素之一。与此同时，年轻群体对健康管理的认知与需求正在快速提升，越来越多的人开始关注自身的饮食结构与饮食习惯。

然而，用户虽然具有强烈的健康管理需求，却普遍存在一个明显矛盾：

  ------------------------------------------------------------------------------
  核心矛盾：知道需要记录，但不愿意持续记录。
  
  如何降低饮食记录成本、提升用户长期留存率，是健康管理产品亟待解决的关键问题。
  ------------------------------------------------------------------------------

2.2 传统饮食记录存在较高操作成本

目前市场上常见的饮食记录方式主要包括以下五类：

  ------------ ----------------------------------------------------- --------------------------
  记录方式     操作流程                                              主要痛点
  手动输入     打开App → 搜索食品名称 → 选择 → 填写摄入量 → 保存     步骤多、耗时久
  拍照识别     打开App → 对准食物拍照 → 等待识别 → 确认修正 → 保存   需主动拍摄、识别率不稳定
  扫码录入     打开App → 扫描包装条码 → 确认食品 → 填写份量 → 保存   仅适用于预包装食品
  数据库选择   打开App → 分类浏览 → 搜索 → 选择具体食品 → 保存       查找成本高、品种不全
  手动填写     打开App → 手动输入食品名与重量 → 保存                 完全依赖用户主动性
  ------------ ----------------------------------------------------- --------------------------

以用户吃一包薯片为例，传统记录流程为：拿出手机 → 解锁 → 打开APP → 拍照/搜索 → 确认食品 → 填写份量 → 保存记录，全程至少需要7步操作、耗时30秒以上。对于偶尔使用而言问题不大，但对于长期健康管理而言，较高的操作成本是造成用户放弃记录的首要原因。

2.3 现有视觉识别方式存在固有局限

基于摄像头的AI饮食识别可以通过食物外观进行分类，是近年来的技术热点，但该方案存在以下固有局限：

-   仍需主动拍摄：用户必须在每次进食前拿出手机对准食物拍照，并未从根本上解决"主动记录"的问题；

&nbsp;
-   环境信息泄露：摄像头在拍摄食物的同时，可能记录用户周围环境、同桌人员、家庭环境等与饮食无关的个人信息，隐私风险较高；

&nbsp;
-   外观相似性难题：许多食物外观相似（如不同品牌的饼干、不同种类的面包），仅靠视觉难以精确区分；

&nbsp;
-   使用场景受限：在社交场合、办公环境等场景下，拿出手机拍照可能令用户感到尴尬。

EatSense 尝试从声学信息切入，为饮食数据采集提供一种全新的交互方式——用户只需自然进食，手机即可被动感知并完成记录，无需任何主动操作。

5. 产品功能设计

5.1 AI饮食识别模块

AI饮食识别是 EatSense 的核心功能入口。用户进入"AI检测"页面后，点击"开始检测"按钮，系统即通过手机麦克风开始采集进食过程中的声音，并利用轻量AI模型进行实时分析。

5.1.1 功能流程与实现方式

1.  启动检测：用户点击"开始检测"，系统请求麦克风权限，初始化音频采集会话（16kHz采样率、单声道、PCM 16bit）；

&nbsp;
2.  实时音频采集：通过 Flutter 的 audio_stream 或 record 插件获取音频流，以25ms为一帧、10ms帧移进行滑动窗口处理；

&nbsp;
3.  VAD活动检测：对每一帧进行能量阈值判断，检测到进食声音（咀嚼/吞咽）时触发AI推理，静默帧跳过以节省算力；

&nbsp;
4.  特征提取：对有效音频帧执行预加重、分帧、加窗（Hann窗）、FFT、Mel滤波器组、对数压缩，生成128×128 Mel频谱图；

&nbsp;
5.  AI推理：将Mel频谱图输入TFLite部署的MobileNetV3-Small模型，输出各类别概率分布；

&nbsp;
6.  结果聚合：对连续多帧的推理结果进行滑动窗口投票（如取最近10帧的众数），消除单帧误判，输出稳定识别结果；

&nbsp;
7.  结果展示：界面显示识别食物名称、置信度百分比、食物属性标签（脆性/软性/液体等）。

5.1.2 初期识别类别规划

初期计划选择约4～8种声学特征差异明显、易于区分的典型食品作为识别类别：

  -------- --------- ---------- ----------------------------------
  类别     英文      食物属性   声学特征描述
  薯片     Chips     脆性食品   高频脆裂声，频谱能量集中在2-8kHz
  饼干     Cookie    脆性食品   中高频碎裂声，持续时间较短
  苹果     Apple     脆爽果蔬   清脆断裂声，首峰能量高，衰减快
  胡萝卜   Carrot    脆爽果蔬   高频纤维断裂声，频谱较宽
  面包     Bread     软性食品   低频咀嚼声，能量集中在0.5-2kHz
  坚果     Nuts      硬脆食品   短促高频爆裂声，峰值能量极高
  面条     Noodles   软性食品   连续吸吮+咀嚼混合声，节律明显
  饮料     Drink     液体       吞咽声+液体流动声，低频为主
  -------- --------- ---------- ----------------------------------

具体类别将根据实际数据集可获得性和模型训练结果进行动态调整，优先保证类别间声学特征的可区分性。

5.2 自动饮食日志模块

AI识别结果将自动进入用户饮食记录，无需用户手动输入任何信息。

5.2.1 日志数据结构

每条饮食日志记录包含以下字段：

  -------------- ---------- --------------------------------------------
  字段名         数据类型   说明
  记录ID         String     唯一标识符，UUID生成
  进食时间       DateTime   识别到进食行为的时间戳，精确到分钟
  食物类别       String     AI识别的食物名称，如"薯片"
  食物属性       String     脆性/软性/液体/果蔬等分类标签
  置信度         Float      AI模型输出的Top-1置信度，0-1之间
  进食时长       Int        本次进食持续秒数
  咀嚼次数       Int        估算的咀嚼动作次数
  平均咀嚼间隔   Float      相邻咀嚼动作的平均时间间隔（秒）
  进食速度评级   String     偏快/正常/偏慢，基于咀嚼间隔与时长综合判断

&nbsp;

&nbsp;
-   数据导出：支持将饮食日志导出为CSV格式，方便用户进行个人数据分析。

5.3 饮食行为分析模块

EatSense 不仅关注"吃了什么"，更关注"怎么吃"。系统从多个维度对用户饮食行为进行量化分析。

5.3.1 进食时长

实现方式：从VAD检测到首次进食声音开始计时，到连续超过30秒无进食声音时结束计时，得到本次进食的总时长。

展示示例：本次进食持续4分23秒。

5.3.2 咀嚼次数

实现方式：对音频信号进行包络提取，通过峰值检测算法识别咀嚼动作的个数。具体步骤为：对音频帧计算RMS能量 → 滑动平均平滑 → 局部峰值检测 → 阈值过滤（排除吞咽声、环境噪声等非咀嚼峰值）→ 计数。

展示示例：本次约45次咀嚼。

5.3.3 咀嚼节律

实现方式：计算相邻两次咀嚼峰值之间的时间间隔，取平均值与标准差，反映用户咀嚼的规律性。

展示示例：平均咀嚼间隔0.7秒，节律稳定。

5.3.4 进食速度

实现方式：综合咀嚼间隔（越短越快）、单位时间咀嚼次数（越多越快）、进食总时长三个指标，通过规则引擎将进食速度分为"偏快/正常/偏慢"三个等级。

展示示例：当前进食速度：偏快（建议放慢节奏，每口咀嚼20次以上）。

5.3.5 饮食规律统计

基于历史记录，系统按日/周维度统计以下指标：

-   每日进食次数与时间分布；

&nbsp;
-   零食次数（非正餐时段的进食记录）；

&nbsp;
-   晚间进食次数（20:00以后的进食记录）；

&nbsp;
-   不同时间段进食频率热力图；

&nbsp;
-   一周饮食规律变化趋势。

5.4 健康分析模块

系统基于用户已有的饮食记录和行为数据，通过规则引擎生成健康管理建议。

5.4.1 周度健康报告示例

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  本周饮食分析（9月3日 - 9月9日）
  
  -   零食次数：较上周增加20%（本周8次 vs 上周6次）
  
  &nbsp;
  -   晚间进食：3次（主要集中在周三、周五、周日）
  
  &nbsp;
  -   平均进食速度：偏快（平均咀嚼间隔0.5秒）
  
  &nbsp;
  -   饮食规律性：有所下降（正餐时间偏差增大）
  
  健康建议：近期下午零食频率较高，可以适当减少高加工零食（如薯片、饼干）的摄入，并增加水果（如苹果）等健康食物的选择。同时建议放慢进食速度，每口食物咀嚼20次以上，有助于提升饱腹感、减少过量摄入。
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

5.4.2 健康建议生成逻辑

健康建议基于以下规则维度生成：

  ------------ ------------------------------ -----------------------------------
  分析维度     判断规则                       对应建议

  食物多样性   周食物类别≤3种                 建议丰富饮食种类，均衡营养

-   实现方案：Flutter端使用 record 或 audio_stream 插件获取实时音频流，Android端基于AudioRecord API，iOS端基于AVAudioEngine；

&nbsp;
-   缓冲策略：采用环形缓冲区存储最近1秒音频数据，支持实时处理与回溯；

&nbsp;
-   权限管理：首次使用时请求麦克风权限，提供权限说明与引导。

6.3.2 音频预处理模块

_y_[_n_]=_x_[_n_]−0.97 ⋅ _x_[_n_ − 1]

-   分帧加窗：帧长25ms（400个采样点）、帧移10ms（160个采样点），使用Hann窗减少频谱泄漏；

&nbsp;
-   降噪处理：采用谱减法（Spectral Subtraction）进行基础降噪，估计噪声频谱并从信号频谱中扣除；

&nbsp;
-   音量标准化：对每帧音频进行RMS归一化，消除不同手机麦克风增益差异带来的影响；

&nbsp;
-   VAD检测：基于短时能量与过零率的双门限VAD算法，区分进食声音与静默/环境噪声。

6.3.3 MEL频谱特征提取

-   FFT变换：对每帧执行512点FFT，得到幅度谱；

&nbsp;
-   MEL滤波器组：使用128个Mel滤波器，模拟人耳听觉特性，将线性频率映射到Mel频率尺度；

&nbsp;
-   对数压缩：对滤波器输出取对数，模拟人耳对响度的非线性感知；

&nbsp;
-   特征图生成：将连续128帧的Mel频谱拼接为128×128的二维特征图，作为CNN模型的输入；

&nbsp;
-   标准化：对特征图进行Z-Score标准化，加速模型收敛。

7. AI模型方案

7.1 模型选择与理由

初期采用 MOBILENETV3-SMALL 作为核心分类模型，主要考虑如下：

  ------------ -------------------------------------------------------------------------
  选型维度     MobileNetV3-Small 的优势
  模型体积     参数量约2.5M，模型文件约10MB（FP32）/ 2.5MB（INT8量化），适合移动端部署
  推理速度     在中端手机上单帧推理约30-50ms，可满足实时处理需求
  移动端适配   专为移动设备设计，支持TFLite完整转换与硬件加速（NNAPI / Core ML）
  分类能力     基于ImageNet预训练，迁移学习后可满足少类别食品分类任务
  部署便利性   支持TensorFlow Lite完整工具链，量化、优化、部署流程成熟
  ------------ -------------------------------------------------------------------------

7.2 模型训练方案

7.2.1 迁移学习策略

1.  预训练权重：使用ImageNet预训练的MobileNetV3-Small权重作为初始化；

&nbsp;
2.  冻结底层：训练初期冻结前80%层，仅训练顶层分类器，避免小数据集下过拟合；

&nbsp;
3.  微调顶层：分类器收敛后，解冻顶层20%层，使用较小学习率（1e-5）进行微调；

&nbsp;
4.  分类头替换：将原1000类全连接层替换为适配食品类别数的全连接层 + Softmax。

7.2.2 训练超参数

  ------------ -----------------------------------------------
  超参数       设置值
  优化器       AdamW
  初始学习率   1e-3（分类器阶段）/ 1e-5（微调阶段）
  学习率调度   Cosine Annealing
  Batch Size   32
  Epochs       50（含早停）
  损失函数     Cross Entropy Loss + Label Smoothing（ε=0.1）
  早停策略     验证集Loss连续5轮不下降则停止
  ------------ -----------------------------------------------

7.3 数据增强方案

为模拟真实移动端使用场景，提高模型在非理想环境下的鲁棒性，训练阶段采用以下数据增强策略：

  -------------- ------------------------------------------ ------------------------------
  增强方式       具体操作                                   模拟场景
  环境噪声混合   按信噪比5-20dB混合餐厅、人声、街道等噪声   真实就餐环境噪声
  音量变化       随机缩放0.5-2.0倍音量                      手机距离差异、麦克风增益差异
  混响模拟       添加不同房间冲激响应（RIR）                不同房间声学环境
  时间变换       随机时间拉伸0.8-1.2倍、随机裁剪            不同进食速度
  SpecAugment    随机时间掩码（T=10）、频率掩码（F=8）      提升频谱鲁棒性
  Mixup          按α=0.2的Beta分布混合样本与标签            提升模型泛化能力
  -------------- ------------------------------------------ ------------------------------

7.4 模型评估指标

模型效果通过以下指标进行量化评估，并在项目计划书中展示：

-   TOP-1准确率（ACCURACY）：整体分类正确率；

&nbsp;
-   精确率（PRECISION）：每类预测为正的样本中实际为正的比例；

&nbsp;
-   召回率（RECALL）：每类实际为正的样本中被正确预测的比例；

&nbsp;
-   F1分数：Precision与Recall的调和平均；

&nbsp;
-   混淆矩阵：可视化各类别间的误分类情况；

&nbsp;
-   推理延迟：移动端单帧平均推理时间（ms）。

10. 隐私保护设计

EatSense 将"端侧AI"作为核心技术特色与隐私保护基石，从架构层面保障用户数据安全。

10.1 传统云端AI VS EATSENSE端侧AI

  -------------------------------------------------------------------- ------------------------------------------------------------------------------
    ----------------------------------------------------------------     --------------------------------------------------------------------------
    传统云端AI模式                                                       EATSENSE端侧AI模式
                                                                         
    用户声音 → 上传服务器 → 云端AI处理 → 返回识别结果                    用户声音 → 手机本地处理 → 端侧AI推理 → 生成结构化结果 → 原始音频即时删除
                                                                         
    _原始音频需上传云端，存在网络传输与服务器存储的隐私泄露风险。_       _原始音频永不离开设备，仅保留结构化的饮食记录数据。_
    ----------------------------------------------------------------     --------------------------------------------------------------------------
                                                                       
  -------------------------------------------------------------------- ------------------------------------------------------------------------------

10.2 隐私保护具体措施

1.  原始音频本地处理：所有音频采集、预处理、特征提取与AI推理均在手机本地完成，原始音频默认不上传任何服务器；

&nbsp;
2.  音频即时删除：AI推理完成后，原始音频数据立即从内存中释放，不做本地持久化存储；

&nbsp;
3.  仅存储结构化数据：本地数据库仅存储食物类别、时间、置信度等结构化文本数据，不存储任何音频文件；

&nbsp;
4.  数据不出设备：饮食日志等用户数据默认仅存储在本地，用户可主动选择导出，但不会自动同步至云端；

&nbsp;
5.  最小权限原则：App仅请求麦克风权限（用于音频采集），不请求通讯录、位置、相机等无关权限；

&nbsp;
6.  透明隐私政策：在产品中明确告知用户数据处理方式，用户可随时查看与管理自己的数据。

11. 项目创新点

11.1 创新点一：声学饮食感知

区别于传统的视觉识别和手动记录方式，EatSense 创新性地利用进食声音作为饮食数据采集入口。咀嚼声、吞咽声等声学信号蕴含丰富的食物质地信息，为饮食识别提供了一条全新的技术路径。与视觉方案相比，声学感知无需用户主动拍摄，可在自然进食过程中被动完成数据采集。

11.2 创新点二：无感饮食记录

用户无需频繁进行"拍照 → 输入 → 搜索 → 确认"的操作流程，而是通过自然进食行为即可完成数据采集。系统在后台被动感知与记录，将饮食记录的操作成本降为零，从根本上解决了"用户无法坚持记录"这一行业核心痛点，显著降低长期健康管理的使用门槛。

11.3 创新点三：从"吃什么"到"怎么吃"

项目不仅关注食品类别识别（"吃了什么"），还进一步深入分析饮食行为维度（"怎么吃"），包括进食时间、咀嚼节律、进食速度、零食频率、饮食规律等多维度指标。实现从单纯食品识别向饮食行为分析的延伸，为健康管理提供更全面、更有价值的洞察。

11.4 创新点四：端侧隐私AI

将轻量化深度学习模型部署到移动设备，在本地完成全部AI推理，原始音频默认不上传云端。在提供AI能力的同时，从架构层面保障用户隐私安全，契合当前数据安全与个人信息保护的政策导向与用户需求。

15. 项目风险及解决方案

  ------- ------------------------ -----------------------------------------------------------------------------------------------------------------------------------------------------------------------
  编号    风险描述                 解决方案

17. 项目发展规划

17.1 第一阶段：原型验证（当前）

完成"声音采集 → AI识别 → 自动记录 → 健康建议"的完整产品闭环，验证声学感知在无感饮食管理场景下的技术可行性与产品价值。目标是在竞赛中展示核心概念与技术实现，获得初步认可。

17.2 第二阶段：真实场景优化

在原型验证基础上，围绕真实场景可用性进行深度优化：

-   增加更多用户数据（不同人群、不同饮食习惯）；

&nbsp;
-   覆盖更多手机设备与操作系统版本；

&nbsp;
-   采集更多环境数据（食堂、餐厅、办公室、户外等）；

&nbsp;
-   扩展食品类别至15～20类，覆盖主流日常饮食；

&nbsp;
-   提升实际使用场景下的识别准确率与稳定性。

17.3 第三阶段：智能健康管理平台

进一步建立用户饮食画像，实现从"记录工具"到"智能健康管理平台"的升级：

-   饮食记录 → 行为分析 → 趋势预测 → 个性化建议的完整闭环；

&nbsp;
-   引入大语言模型，实现自然语言交互的AI健康助手；

&nbsp;
-   探索与运动、睡眠、体重等健康数据的融合；

&nbsp;
-   支持蓝牙耳机、智能手表等多设备采集；

&nbsp;
-   探索B端合作（健康管理平台、保险公司、企业健康福利等）。

18. 项目最终定位

  ------------------------------------------------------------------------------------
  EatSense 不是单纯的"AI食物分类器"，而是一款：
  
  以声学感知为入口、以端侧AI为技术基础、以无感记录为核心体验的智能饮食健康管理助手。
  ------------------------------------------------------------------------------------

项目希望解决的核心问题是：让用户不需要为了健康管理而频繁记录，而是在自然进食过程中自动形成饮食数据。

最终愿景：

让记录饮食，从"动手"变成"无感"。

_EatSense——让手机听见每一餐，帮助用户理解自己的饮食习惯。_

_本项目计划书为初版，将根据项目进展持续迭代更新。_
