## 1. 结论先行：软件一共有多少功能

| 口径 | 数量 | 说明 |
|---|---|---|
| **候选功能总数**（材料中提出过的全部功能） | **47** | 见 §2 + §4 |
| **v1.0 交付功能** | **40** | 见 §2，每项一份 spec + 一份 plan（共 80 份文档） |
| 🆕 **v2.0 新增功能**（`ADR-44` 云端 Agent） | **+5** | 见 §2.5（`G-01` `G-02` `G-03` `U-07` `C-06`），另加一份跨端契约 `API-07` |
| 🆕 **现行交付功能合计** | **45** | 40（v1.0，**范围一字未动**）+ 5（v2.0） |
| 其中「降级交付」 | 3 | `D-04`（无登录，改本地档案）、`A-04`（演示数据双轨）、`U-05`（成就仅静态展示） |
| 其中「硬闸门」功能（不过则全项目退回） | 4 | `P-04` `T-07` `T-08` `C-03` |
| **已裁剪功能**（登记不交付） | **7** | 见 §4，释放约 3.5 人日 |
| **推迟到后续阶段**（写进 PPT「后续工作」） | 12 | 见 §5 |

**为什么不是「9 个功能模块」**：主方案 §4.1 的 9 条是**材料层面的粗颗粒度模块**，其中每一条都包含若干**独立的技术契约与验收对象**（例如第 3 条「Mel 频谱特征提取」实际上包含「Kotlin 原生 FFT/滤波器组实现」和「与 librosa 的跨语言数值对齐」两个完全不同的可验收对象，后者是全项目风险最高的环节之一）。按模块粒度写 spec 会导致**验收标准无法落到具体产物上**，也无法定位责任。

**为什么也不是「越细越好」**：拆到每个函数会得到 200+ 项，其中大量条目没有独立契约与独立验收方式，spec 会退化为代码注释的复述。本清单采用**「一个功能 = 一个可独立验收的产物 + 一条可机器判定的判据」**为拆解原则。

**拆解原则（三条）**：
1. **有独立产物**：能指向具体文件（`.dart` / `.kt` / `.tflite` / `.json` / 页面）或具体运行行为。
2. **有独立验收方式**：能用命令、测试名或核对表判定通过/不通过。
3. **有独立失败后果**：它坏了，别人不会跟着一起坏（即不是纯粹的代码组织单元）。
