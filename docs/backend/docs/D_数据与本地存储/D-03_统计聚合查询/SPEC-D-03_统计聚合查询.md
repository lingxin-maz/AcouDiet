## 1. 目标与范围
### 1.1 一句话目标
用 SQL 聚合出**今日汇总、本周汇总、7 天趋势序列、三餐时间分布与 σ**，并把「正餐 / 零食 / 晚间进食」的时段判定写成可机器验证的规则；**只产出数字，不产出任何分数**。
### 1.2 范围内（In Scope）
1. `StatsRepo` 的 4 个方法：`today()` / `week()` / `trend(int days)` / `mealTimes(int days)`（签名以 **API-03 §5** 为准）。
2. 时段判定口径：三餐窗口、`snackCount`、`lateNightCount`（§4.1，可测规则；**这是 API-03 §11 问题 2 要求本 SPEC 冻结的常量**）。
3. `mealTimeStdDevMinutes` 的实现落点；口径权威在 **API-03 §5.3**，本 SPEC 只负责把它落成可测实现。
4. `WeekSummary.classCounts`（6 键齐全）与 `estimatedKcal` 的填充方式（经 `KcalResolver` 端口，API-03 §3）。
5. 日期区间计算：设备本地时区的日历日、`yyyy-MM-dd` 键、半开区间 `[startMs, endMs)`。
6. 查询性能预算与索引命中要求（API-00 §3.7；`trend`/`mealTimes` **禁止 N+1**，API-03 §5）。
### 1.3 范围外（Out of Scope）——必须显式写出，防止实现方自由发挥
1. **不定义评分公式、四维权重、评级枚举、`HealthScore` / `DimensionScore`** —— 属 `SPEC-A-01` / `API-04`。本功能只把 σ、计数、热量交给它。
2. **不填充 `TrendPoint.totalScore`**：L3 **恒为 `null`**（API-03 §5），由 `API-04` §5 的 `ReportService.trend()` 在 L4 合并。
3. **不定义「类别 → 属性/标准份量/热量」的数值** —— 属 `SPEC-P-08`；本功能只调用 `KcalResolver` 端口。
4. **不写表结构与索引** —— 属 `SPEC-D-01`；**不写 DAO 与迁移** —— 属 `SPEC-D-02`。
5. **不做**物化聚合表（除 §10 问题 4 另有结论）、不做缓存、不做分页、不做数据导出。
6. **不做**任何格式化：不产出 `"85 分"`、`"约 1100 kcal"`、`"12 分 34 秒"` 之类字符串（API-00 §3.2、API-05 §6.2）。

## 2. 功能行为
### 2.1 触发与前置条件
| 触发 | 前置条件 |
|---|---|
| 首页 / 记录页 / 报告页进入（`U-01` / `U-03` / `U-04`） | 由 Riverpod provider 按需触发一次；**不预加载全表**（API-05 §5.4） |
| `trend(days)` / `mealTimes(days)` 调用 | `days ∈ [1,365]`（API-03 §5）；越界 → `ACD-DB-004`（`retryable:false`） |
| 库为空 | 四个方法都返回**零值对象**，不得抛异常 |
| 句柄未打开 | 由 `SPEC-D-02` 的 `AppDatabase` 先完成 `open()`；本功能不负责建库 |
| `KcalResolver` 未装配 | 装配层必须注入；未注册 `classId` → `ACD-KB-001`（API-03 §3） |
### 2.2 主流程（编号步骤）
1. 由 Dart 用设备本地时区算出半开区间 `DateRange{startMs, endMs}`：今日 = 本地 `00:00:00.000` → 次日同刻；本周 = 最近 7 个本地日历日（含今日，API-03 §5）；`days` 天 = 含今日在内往前数 `days` 个日历日。**区间换算由 L4 调用方完成**（API-03 §4）。
2. `today()`：一条 SQL 出该区间的**按类计数**与分钟序列所需字段；`recordCount` / `snackCount` 由计数得出，`estimatedKcal = Σ KcalResolver.kcalFor(classId)`，`records` 用 `DietRepo.byRange` 取（避免两份真相）。
3. `week()`：一条 SQL 出 `recordCount` / `snackCount` / `lateNightCount` / `classCounts`；`estimatedKcal` 同 §2.2-2；σ 由 §4.3 的两级步骤算出。
4. `trend(days)`：一条 SQL 按本地日历日 `GROUP BY`，Dart 侧补齐缺失日并按日期升序返回恰好 `days` 个 `TrendPoint`。
5. `mealTimes(days)`：一条 SQL 按本地小时 `GROUP BY`，Dart 侧补齐 0–23 全部键（缺省 0）。
6. 所有返回值均为值对象，**不持有 `Database` 引用**，不在方法间共享可变状态。
### 2.3 状态与状态迁移（有状态的功能必填，无状态写「无状态」）
**无状态**。四个方法都是只读纯查询，不写库、不缓存。因此「同库 + 同参数 + 同一时区 → 逐字段相同」，满足 API-05 §6.1 与 API-03 §5 的可复现性要求。
### 2.4 边界条件
| 边界 | 规定 |
|---|---|
| 空库 | `today()` → `{recordCount:0, estimatedKcal:0, snackCount:0, records:[]}`；`week().mealTimeStdDevMinutes == null` 且 `classCounts` 仍为 6 键全 0；`trend(n)` 仍返回 `n` 个点（全 `null`） |
| σ 无可采纳餐类 | 返回 `null`，**不得返回 `0`** —— `0` 表示「三餐时间完全一致」，与「无足够数据」语义不同（API-03 §5.3） |
| 跨午夜会话 | 归属由 `eaten_at_ms` 决定；`ended_at_ms` **不参与**分日与时段判定（口径唯一） |
| `behavior_metrics` 为全 `NULL` 占位行 | 对本功能**四个方法的输出没有任何影响** —— 本功能不读指标列值。这正是 1:1 硬约束（API-03 I-1）换来的确定性 |
| `source` 为 `demo` 的记录 | 与 `real` 记录**同等参与**聚合；`countAll` / `recordCount` 一并计数（API-03 §4）。分流方案见 §10 问题 2 |
| `KcalResolver` 收到未注册 `classId` | **不得**兜底记 0，必须抛 `ACD-KB-001`（API-03 §3） |
| 同一毫秒两条记录 | 均计入；`byRange` 排序键为 `eaten_at_ms`，同值顺序不保证 |
| 时区/夏令时 | 区间由 Dart 本地日历日算得；测试必须固定时区（注入时钟/时区） |
| `trend` / `mealTimes` 的实现方式 | **禁止 N+1**：不得「逐日一次查询」或「逐小时一次查询」，必须单条 `GROUP BY`（API-03 §5） |

## 4. 数据契约
### 4.1 餐次窗口与时段判定口径（**权威定义已迁移至 `API-03` §5，本表按 A-2 修订同步**）
| 时段 | 本地小时区间 | 判定结果 |
|---|---|---|
| 早餐 | `[05:00, 10:00)` | 正餐 |
| 午餐 | `[11:00, 14:00)` | 正餐 |
| 晚餐 | `[17:00, 21:00)` | 正餐 |
| **零食 / 加餐**（`snackCount`） | 不落入上述任一正餐窗口，即 `[10:00,11:00)` ∪ `[14:00,17:00)` ∪ `[21:00,05:00)` | 零食 |
| **晚间进食**（`lateNightCount`） | `[20:00, 05:00)` | 晚间 |
> 判定只依赖 `eaten_at_ms` 换算到**设备本地时区**的钟点，**与系统当前时间无关**（可复现性）。零食与晚间**刻意允许重叠**：`[21:00,05:00)` 同时计入两者。**这不是缺陷** —— 它们是两个不同的产品指标（加餐频率 vs 夜间进食），不是互斥分类，**不得"去重"**。
>
> 🔴 **A-2 修订说明（本表原值已作废）**：原值为 早 `[05,11)` / 午 `[11,16)` / 晚 `[16,23)`，其后果是零食窗口被压缩到仅剩 `[23:00,05:00)`、与 `lateNightCount` **完全重合**，使 FF-22 的 `snack` 维度（100 分制中的 20 分）几乎恒为满分而**失去区分度**；并且 15:40 的下午加餐会被计为**午餐正餐**，与 `软件UI界面设计图/3.png`「15:40 薯片 / 下午零食」及主方案 §5.4.1「近期下午零食频率较高」矛盾；也与 `计划书 v1.txt` §5.3.5「晚间进食 = 20:00 以后」不一致。**完整裁定见 `API-03` §5 的 A-2 条目。**
> **本 SPEC §10 问题 1 已随之关闭。**
> **测试夹具同步（§7 判据 2）**：边界钟点由 `04:59,05:00,10:59,11:00,15:59,16:00,22:59,23:00` 改为 `04:59,05:00,09:59,10:00,10:59,11:00,13:59,14:00,16:59,17:00,19:59,20:00,20:59,21:00`，三条零食窗口与晚间窗口各放 1 条断言。
### 4.2 汇总字段的填充口径
| 字段 | 口径 | 可空 |
|---|---|---|
| `recordCount` | 区间内 `COUNT(*)`（真实 + 演示一并计数） | 否 |
| `estimatedKcal` | `Σ KcalResolver.kcalFor(classId)`，由 SQL 出按类计数后求和（API-03 §3） | 否 |
| `snackCount` | 区间内钟点落在 §4.1 零食窗口的 `COUNT(*)` | 否 |
| `lateNightCount` | 区间内钟点落在 §4.1 晚间窗口的 `COUNT(*)` | 否 |
| `classCounts` | 键 = FF-19 英文类名，**必须包含全部 6 个键**（缺失补 0，API-03 §5） | 否 |
| `records` | `DietRepo.byRange` 结果，按 `eatenAtMs` 升序（空则空列表） | 否（可空列表） |
| `mealTimeStdDevMinutes` | §4.3 口径；无采纳餐类 → `null` | **是** |
| `byHour` | 键 = 本地整点 `0..23`，**必须具备全部 24 个键**（缺补 0） | 否 |
### 4.3 σ 的实现口径（**权威在 API-03 §5.3，本 SPEC 只落成可测步骤**）
1. 按 §4.1 把区间内记录分入**早餐 / 午餐 / 晚餐**三类；**零食不计入**。
2. 每类内把 `eaten_at_ms` 换算为**本地当日 00:00 起的分钟数** `t = hour × 60 + minute`，跨日历日计算**样本标准差**（分母 `n − 1`）。
3. **仅采纳样本数 `n ≥ 2` 的餐类**（`n = 1` 的餐类不参与，因为样本标准差无定义）。
4. 结果为采纳餐类标准差的**算术平均**；**无采纳餐类 → `null`**。
5. 单位分钟（`double`），**不取整**。FF-22 中 `σ ≤ 30 → 满分 / σ ≥ 90 → 零分` 的公式与评级属 `SPEC-A-01`（`API-04` §3 的 `evidence.sigmaMinutes` 直接消费本字段），**本功能不实现、不重算**。
6. **禁止**改用「池化组内标准差」或「三类均值之间的离散度」等其它口径 —— 一旦与 API-03 §5.3 / `SPEC-A-01` 不一致，`regularity` 维度即不可复现。
### 4.4 趋势点
| 字段 | 口径 |
|---|---|
| `TrendPoint.date` | 本地日历日字符串 `yyyy-MM-dd`（API-00 §3.2） |
| `TrendPoint.estimatedKcal` | 该日热量和；**该日无记录时恒为 `null`**，**不写 `0`**（API-03 §5） |
| `TrendPoint.totalScore` | **恒为 `null`**（本功能不产出分数，API-04 §5 在 L4 填充） |
### 4.5 索引使用与查询骨架
```sql
-- 区间计数 + 按类计数（时段判定在派生列 h 上做，不破坏索引）
SELECT CAST(strftime('%H', eaten_at_ms/1000, 'unixepoch', 'localtime') AS INTEGER) AS h,
       class_id, COUNT(*) AS c
FROM diet_record WHERE eaten_at_ms >= ? AND eaten_at_ms < ?
GROUP BY h, class_id;
```
- 四条查询的 `WHERE` 只允许出现 `eaten_at_ms` 的**区间比较**；**禁止**在 `WHERE` 里对 `eaten_at_ms` 做函数包装（否则索引失效，判据 8 直接失败）。
- **禁止 N+1**：`trend(days)` 必须一条 `GROUP BY date(...)`；`mealTimes(days)` 必须一条 `GROUP BY hour`（API-03 §5）。
- `estimatedKcal` **不在 SQL 内计算**（L3 无热量数据）：SQL 只出按类计数，求和由实现类经 `KcalResolver` 完成（API-03 §3）。

## 6. 异常与降级
| 异常 | 检测方式 | 处理 | 用户可见表现 |
|---|---|---|---|
| 查询事务失败（`ACD-DB-003`） | `DatabaseException` 非约束类 | 转 `AcouDietError`，向上抛给 provider | 页面显示错误态 + 重试按钮，**不得崩溃** |
| 入参非法 / 表列缺失（`ACD-DB-004`） | `days` 越界、`DateRange` 反序、schema 不符 | 抛 `ACD-DB-004`（不重试，属调用方缺陷） | 页面错误态 |
| `KcalResolver` 未注册类（`ACD-KB-001`） | 端口抛错 | 抛出，**禁止**兜底 0 | 首页/报告页错误态，热量显示「—」而非 0 |
| 空结果集 | 行数为 0 | 返回零值对象（不抛异常、不返回 `null`） | 空态文案由 `U-06` 的空态组件负责 |
| 查询计划出现 `SCAN diet_record` | 判据 8 的 `EXPLAIN QUERY PLAN` 断言 | 视为**缺陷**，修 SQL 或索引，**不做运行时降级** | 无 |
| 性能超预算 / 出现 N+1 | 判据 9、判据 10 | 视为缺陷（同 `PLAN-D-03` §6） | 无 |
