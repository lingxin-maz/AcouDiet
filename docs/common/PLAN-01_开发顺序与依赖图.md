## 1. 排序三原则

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **风险优先，不是难度优先** | `P-04`（Kotlin Mel）失败 → `T-08` 挂 → `T-07` 的模型不可用 → **项目归零**。而 UI 丑、报告页不好看**都能靠加班补**。不确定性最高的必须最先做掉。 |
| 2 | **接口冻结先于并行** | 三个人一旦各写各的常量，就是 §3.1 那种「D5 联调才炸」的坑。**D1 冻结三个接口之后，才存在真并行。** |
| 3 | **占位数据解耦** | C 的页面用 `FakeRepo`，**不等 B 的数据库**；B 完成后切 `RealRepo`，**页面代码不改**（`PLAN-00` §4）。 |

> 反面做法（本项目最容易犯的错）：先做 UI → 先做数据库 → 最后碰音频。这样风险最高的环节被推到最后，**一旦 `P-04` 出不来，前面全白做**。

## 7. 两个会改变顺序的岔路口

### 岔路口 ①：`P-04` 触发 Plan-S（D2 结束仍未产出数组）

顺序变为：**跳过序 9–11 的自写实现，直接接 TFLite Task Library 的 `AudioClassifier`**（其内置 Mel 前端参数与 FF-01~FF-05 一致）。
**代价**：Task Library 内部不接受 `power_to_db(patch_max)` + 逐 patch min-max 的链路干预 → **`SPEC-T-08` 的判据口径要同步改**（`SPEC-P-04` §10 第 6 条已登记该冲突）。
**影响范围**：只动 B 的序 9–11 与 `T-08`；**A 的序 10–13 与 C 的序 7、20–22 全部不受影响**。

### 岔路口 ②：CP1 未过（D3 现场 10 次实拍 <6/10）

动作：**6 类 → 4 类**（脆性/软性/果蔬/液体）→ **A 的序 10、12、13 重跑一轮**。
**影响范围**：只影响 A。**B 的关键路径不受影响**（Mel 前端与类别数无关），**C 的页面也不受影响**（类别只是文案与图标）。仍 <6/10 → 主张转向「行为分析」（保留 `P-07` + `A-01` + `A-03`）。
