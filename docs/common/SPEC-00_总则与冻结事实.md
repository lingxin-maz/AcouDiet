**三部分怎么分（唯一判据：主要实现位置）**

| 部分 | 判据 | 内容 | 数量 |

**规则**：
1. **spec 与 plan 严格分离**。spec 回答「做什么、怎样算做对」；plan 回答「谁、什么时候、用什么方法、交什么」。spec 里不写排期，plan 里不重新定义行为。
2. **一切验收标准必须机器可判**。写不出可执行判据的条目，不许进 spec（见 §7）。
3. **每个 spec 必须有一个同编号的 plan**，反之亦然。编号一一对应，缺一即为缺陷。**例外是 `SPEC-00` / `PLAN-00` / `PLAN-01`**（章节级文档，位于 `common/` 根下，本就不成对）。
4. **引用一律用编号，不用路径**：写 `API-03`、`SPEC-P-04`、`PLAN-C-03`，**不要写文件路径**。这样重组目录时不会产生失效引用（本次重组已充分证明这一点）。需要指整个目录时用 glob：`docs/*/docs_api/`。

## 3. 冻结事实（Frozen Facts）

> **本节数值不得在 spec/plan 中"重新定义"或"就近取整"。** 需要引用时**直接引用编号**（如「见 SPEC-00 §3.1 FF-06」），不要复制出第二份可能漂移的数字。
> `feature_config` 是这些数值的机器可读版本；本节是它的中文说明与推导。

### 3.1 音频与特征（FF-01 ~ FF-12）

| 编号 | 项 | 冻结值 | 备注 |
|---|---|---|---|
| FF-01 | 采样率 | `16000` Hz | 单声道、PCM 16-bit |
| FF-02 | 预加重 | `0.97` | `y[n] = x[n] − 0.97·x[n−1]`。**边界（`ADR-21` 修订）**：**沿流取前一原始样本** —— 当前 patch 的首样本用「patch 开始前的最后一个**原始**（未预加重）样本」，源起点用 `0`；`feature_config.preemphasis_boundary = "continuous_stream_previous_raw_sample_or_zero_at_source_start"`。~~`x[−1] = x[0]`（首样本原样通过，`ADR-17`）~~ —— 旧规则只在"每个 patch 都从录音开头开始"时自洽，而 patch 以 0.5 s 步长滑动、每个 patch 有 87.8% 的音频已在上一 patch 被预加重过，逐 patch 重启滤波器会把不连续点放在模型最爱看的位置 |
| FF-03 | 窗函数 | Hann | `win_length = n_fft = 1024`。**STFT 填充（`ADR-16`）**：`center = true` 时 `pad_mode = "constant"`（**零填充**，librosa 默认；`reflect` 已否决）；`feature_config.pad_mode = "constant"` |
| FF-04 | `hop_length` | `512`（32 ms） | **不是 160** |
| FF-05 | `n_mels` / `fmin` / `fmax` | `128` / `20` Hz / `8000` Hz | **Mel 滤波器组（`ADR-16`）**：`htk = false`、`norm = "slaney"`（Slaney 刻度 + Slaney 面积归一化，librosa 默认；`htk = true` 已否决）→ `feature_config.mel_htk = false`、`mel_norm = "slaney"` |
| FF-06 | 幅度 | power spectrogram，`power = 2.0` | |
| FF-07 | 压缩 | `power_to_db`，`top_db = 80.0` | **`ref`（`ADR-21` 修订）**：`ref =` **本 patch 的最大值**（`"patch_max"`）；`feature_config.power_to_db_ref = "patch_max"`。~~`ref = 1.0`（绝对刻度，`ADR-16`）~~ —— ADR-16 否决 `ref=np.max` 的理由是"会让 FF-08 的截断退化为 patch 相对量、重新引入域偏移"，那条理由**对 ADR-16 当时要冻结的链路成立**；但交付的模型**已按 patch 相对刻度训练**，此时"推理与训练不一致"是更大的误差。`amin = 1e-10`（新增键 `power_to_db_amin`） |
| FF-08 | 归一化 | **`power_to_db`（patch 相对）→ 丢弃尾帧 → per-patch min-max 到 `[0,1]`** | **`ADR-21` 修订**：`normalization = "per_patch_minmax"`；~~固定 dB 截断 `clip(x, −80.0, 0.0)` 再 min-max~~ 已取消，`db_clip_range` 键**已删除**，改为 `normalization_output_min = 0.0` / `normalization_output_max = 1.0` / `normalization_epsilon = 1e-08`。⚠️ **顺序是承重的**：dB 参考与 `top_db` 下限算在**全部 129 帧**上，min-max 窗口是**留下的 128 帧**（见 `feature_config.operation_order`）——先 minmax 再截断会得到不同的数 |
| FF-08b | 响度归一化 | **仅训练侧**（`ADR-17`）：`feature_config.loudness_normalization = "training_only"`、`target_lufs = −23.0` | **推理侧不做 LUFS** —— FF-08 的 patch 相对 dB + 逐 patch min-max 已提供尺度不变性，现场再算一遍只增加开销与一处可能不一致的实现 |
| FF-08c | 高通滤波 | **v1.0 移除**（`ADR-17`）：`highpass = removed_in_v1` | 主方案 §3.7 只保留「预加重 + 响度归一化」，**高通从来不在冻结计划里**；且 `fmin = 20 Hz` 的 Mel 滤波器组已丢弃 20 Hz 以下。**不要重新引入** |
| FF-09 | patch 采样数 | `65536`（= 4.096 s @16 kHz） | |
| FF-10 | `center` | `true` | |
| FF-11 | **`n_frames`** | **`128`**（另见 `raw_mel_frames = 129`） | ✅ **已修订**（`ADR-21`，2026-09-12），见 §3.5。**两个数不要混**：`raw_mel_frames` 是 STFT 原始帧数 `129`，`n_frames` 是**喂给模型的张量宽度** `128` |
| FF-12 | 推理滑窗步长 | `0.5` s（每秒 2 个 patch） | |

**Mel 张量形状与内存布局（强制，`ADR-21` 修订）**：

```
shape      : [1, 128, 128, 1]        # [batch, n_mels, n_frames, channel]
dtype      : float32
值域       : [0.0, 1.0]
行主序索引 : mel[m * n_frames + t]     # m ∈ [0,128) 是 Mel 频带，t ∈ [0,128) 是时间帧
原始帧数   : 129（stft 产出）→ 丢弃尾帧 → 保留 [0, 128)
```

> 🔴 **这是全项目最容易出错的一处**：Kotlin 侧输出的 `FloatArray` 必须是「先频带、后时间」的行主序；Python 侧必须能 `np.frombuffer(buf, '<f4').reshape(128, 128)` 直接还原且与训练侧逐元素一致。**验收方式见 SPEC-T-08。**

### 3.5 ✅ 已修订事实：`n_frames = 128`（`raw_mel_frames = 129`）—— 交付制品倒逼的修订（2026-09-12）

| 项 | 内容 |
|---|---|
| 事实 | librosa `center=True` 时帧数 = `n_samples // hop + 1`。4.096 s（65536 样本 @ hop 512）→ **STFT 产出 129 帧**，这个事实没变，它就是 `raw_mel_frames` |
| **已修订** | **`ADR-21`：窗口仍是 4.096 s，但**丢弃第 129 帧**，喂给模型的张量是 `[1, 128, 128, 1]`** |
| 修订日 / 依据 | 2026-09-12 ／ **`ADR-21`**（`docs/01_裁定记录ADR.md` §3） |
| 为什么必须改 | 交付的模型输入张量实测为 `float32[1,128,128,1]`：128×128 个 float32 = **65536 字节**，而 129 帧的 Mel 是 128×129×4 = **66048 字节** —— 差的不只是"一帧"，是**根本喂不进去**。`ADR-20` 当年登记的"待模型组确认是笔误还是真实形状"，**制品回答了：是真实形状** |
| 为什么不是"改窗口" | 选项 A（保留 128 帧、窗口改 4.064 s）会让 `patch_samples` 变成 65024，与"4.096 s = 2¹⁶ 样本"这条贯穿全部下游文档的事实冲突，而且要重新导出 129 帧的中间量。**ADR-21 的做法是保留 4.096 s 窗口与 129 个 STFT 帧，只在归一化前把尾帧丢掉** —— 与训练侧 `operation_order` 逐字一致 |
| **上一版（supersedes）** | `n_frames = 129`、输入 `[1,128,129,1]`，2026-09-10 由 **`ADR-P1`** 拍板（选项 B）。ADR-P1 的推理 ①「4.096 s 是自然时长」②「129 非 2 的幂对 GAP 分类器无影响」③「4.096 s 已冻结、改选 A 换不来建模收益」**全部仍然成立** —— 它只是没有、也无法预见到训练侧会按 128 帧出制品 |
| 证据 | `_toolchain/probe_released_models.py`（逐制品读 I/O）、`_toolchain/probe_frontend_alignment.py`（计算图前三个算子 + 两个候选前端的端到端对照） |
| 机器可读记录 | `shared/feature_config.json` 的 `_decisions.n_frames`（标注被取代）与 `_decisions.mel_frontend_v1_1`（完整裁定 + `supersedes` + 诚实边界） |

> 🔴 **这是已修订值**：`feature_config.n_frames = 128`、`raw_mel_frames = 129`、`input_shape = [1,128,128,1]`、`frame_selection = {drop_tail, [0,128)}`（生成常量同步）。
> **所有 spec/plan 的写法要求**：写 `n_frames = 128`（引用 FF-11 或 `ADR-21`）；**提到 129 时必须说清它指 `raw_mel_frames`（STFT 原始帧数），绝不能再说它是张量宽度**。这一条正是本次缺陷的成因。
> ⚠️ **改动它的后果**：任何改动都会使已训练权重作废，且必须走 `SPEC-C-03` 的变更传播单。

|---|---|---|
| FF-21a | 进食结束判据 | 首次进食声 → **连续 90 s** 无进食声（**不是 30 s**） |
| FF-21b | 咀嚼峰最小间距 | 200 ms |
| FF-21c | 峰值动态阈值 | 本会话 `μ + 0.5σ` |
| FF-21d | 伪峰过滤 | 排除峰宽 >150 ms 的宽峰；排除前后 300 ms 内无邻峰的孤立峰 |
| FF-21e | 进食速度 | 平均咀嚼间隔 `t < 0.50 s` → 偏快；`0.50–0.80 s` → 正常；`t > 0.80 s` → 偏慢 |
| FF-21f | 咀嚼次数文案 | 必须带「约」：`约 45 次` |
| FF-21g | MAE 降级线 | 咀嚼次数 MAE > 25% → 文案降级为「咀嚼节奏：较快」，**不给绝对数字** |
| **FF-21h** | **包络由原生侧计算** | 帧长 **10 ms**（160 样本）/ hop **5 ms**（80 样本），取短时 **RMS**；随 `patch` 事件以 `rmsEnvelope`（`Float32List`）下发。长度 `floor(patchSamples × 1000 / (sampleRate × envelopeHopMs)) = 819`。**见 `API-01` §7 的架构裁定** |
| **FF-21i** | 行为算法的位置 | **包络计算在 Kotlin（L1），平滑与峰值检测在 Dart（L4）**。理由：与主方案 §3.3「DSP 下沉原生，只把算好的数组传 Flutter」的原则一致；带宽 819 × 4 B ≈ 3.3 KB/事件，而传原始 PCM16 需 131 KB/事件（**约 40 倍**） |
| FF-21j | ❌ 不交付 | 咀嚼节律标准差 σ（`X-07`） |
| **FF-21k** | **VAD 四个参数（`ADR-18`）** | 自适应噪声底 + 余量判定，**全部在 `feature_config.behavior`**：`noise_floor_init = 0.001`（线性 RMS ≈ −60 dBFS）/ `noise_floor_min = 0.0003`（≈ −70 dBFS）/ `voiced_margin_db = 6.0` / `noise_floor_alpha = 0.95`（一阶慢更新，32 ms 帧移下时间常数 ≈ 0.64 s）。判定式：**`rms > noise_floor × 10^(voiced_margin_db / 20)` 即为 voiced**。**用自适应而非固定阈值**：手机麦克风增益跨机型差异极大，绝对阈值无法迁移 |

> ⚠️ **FF-21h/FF-21i 是 `SPEC-P-07` 与 `API-01` 交叉评审后新增的事实**：原设计把 `BehaviorAnalyzer` 的输入定义为「4.096 s patch 的时域波形」（主方案 §5.4），但 `API-01` 的 `patch` 事件并不携带 PCM —— 于是 `P-07` **没有任何数据源**，D7 的硬验收「能输出约 45 次，偏快」无法达成。**本项通过把包络计算下沉原生解决，而不是把 131 KB 的 PCM 塞进每个事件。**

### 3.7 健康评分卡（FF-22）

**总分 = 四维之和，0–100。四项公式全部公开，UI 必须可下钻。**

| 维度 | 满分 | 公式 | 端点 |
|---|---|---|---|
| 饮食规律性 `regularity` | 30 | `30 × max(0, 1 − σ/90min)`，σ = 三餐时间标准差（分钟） | **σ=0 → 30；σ=30 → 20；σ=60 → 10；σ≥90 → 0**（连续线性衰减，**无平台段**） |
| 食物结构 `structure` | 30 | `30 × min(1, p/0.4)`，`p` = (apple + carrot + bread) 占比 | p=0 → 0；p≥40% → 30 |
| 零食控制 `snack` | 20 | `20 × max(0, 1 − n/10)`，`n` = **本周**零食次数 | n=0 → 20；n≥10 → 0 |
| 进食速度 `speed` | 20 | `t ≥ 0.8s → 20`；`t ≤ 0.4s → 0`；中间线性插值 | t=0.8s → 20；t=0.4s → 0 |

> 🔴 **FF-22 已修正一处自相矛盾（`SPEC-A-01` 交叉评审发现，必须知悉）**
> 主方案 §3.8 的**同一格**里既写了公式 `30 × max(0, 1 − σ/90min)`，又写了散文「σ≤30min 满分」。但该公式在 σ=30 min 时给出 `30 × (1 − 1/3) = 20` 分 —— **与「满分」直接矛盾**。
> **裁定：以公式为准，散文表述作废。** 理由：公式是精确、可机器判定的工件；散文是它的不准确摘要。**只改摘要、不改公式**，因此没有引入任何新公式，评分表结构保持冻结。
> **受影响的产物**：`SPEC-A-01` 的「输入→期望分数」算例必须按 σ=30 → 20 计（本表为准）；`PLAN-C-05` 的 `health_score_consistency_test.dart` 断言同上。
> **FF-22b `grade` 分档阈值（已拍板，不再是缺口）**：`总分 ≥ 80 → 良好`、`60 ≤ 总分 ≤ 79 → 一般`、`总分 < 60 → 需改善`。
> 依据 **`ADR-P2`**（2026-09-10 拍板）；机器可读值在 `feature_config.health_score_formula.grade_thresholds`（`good_min = 80`、`fair_min = 60`），消费方为 `API-04` 的 `HealthScore.grade` 与 `U-01`/`U-04` 的评级展示。**与 `1.png` 的「85 分 = 良好」一致。**

- `σ` = 用户**自身历史**三餐时间的标准差（不是固定时刻）。
- 评级枚举：`良好` / `一般` / `需改善`。
- **硬约束**：预置演示数据算出的分数必须与 UI 显示的数字一致，由 `SPEC-C-05` 的单元测试断言。

> 🔬 **FF-22 求值顺序也是冻结约定的一部分（`SPEC-A-01` 交叉评审发现）**
> 四维公式必须按**字面表达式**求值，**不得做代数重排**：
> - ✅ `round(30 × min(1, p / 0.4))`　　❌ `round(30 × p / 0.4)`
> - ✅ `round(30 × max(0, 1 − σ / 90))`
>
> **为什么这条必须写进宪法**：IEEE-754 下二者**不等价**。
> `30 * min(1, 0.30/0.4)` = `30 × 0.7499999999999999` = **`22.499999999999996` → `round` 得 22**；
> 而 `30 * 0.30 / 0.4` = **`22.5` → `round` 得 23**。
> **同一个公式的两种等价写法会给出相差 1 分的总分** —— 而 UI 会把这个数字直接展示给评委。这类分歧在联调时表现为「后端算 22、前端算 23」，且**不会报错**。
>
> **配套要求**：
> 1. 实现与测试都必须使用字面表达式（`PLAN-C-05` 的 `health_score_consistency_test.dart` 负责断言）。
> 2. 评分夹具的比值取**浮点安全值**（`SPEC-A-01` 表 A-01-T3 已采用 `p ∈ {0.10, 0.20, 0.25, 1.00}`），避开 `p / 0.4` 恰为半值的组合。
> 3. **保留一条回归用例**固定记录 `p = 0.30` 在字面表达式下应得 **22**（写死，防止有人"优化"成 23）。
