# API-05 后端数据通讯规范

**上游**：主方案 §6（隐私与合规）、§9（Demo）、`SPEC-00` §3.9（FF-24）、`API-00` §1
**性质**：本文件同时是**接口规范**与**架构裁定记录（ADR）**。它回答一个必须先回答的问题：**AcouDiet 的「后端」是什么？**

---

## 1. 裁定：v1.0 离线；`agent` 风味引入**唯一**的云端出口，且**音频永不出境**

> # ✅ 已修订（`ADR-44`，2026-09-16）
>
> **本节原裁定是「v1.0 不存在任何云端后端、不存在任何网络调用、不存在任何数据出境路径」。**
> 产品定位由「离线端侧识别器」变更为「手机端饮食 Agent」后，该裁定被**修订**，不是被删除：
>
> | 项 | 原裁定（v1.0） | **现行裁定（`ADR-44`）** |
> |---|---|---|
> | 网络出口 | **零**，任何 spec/plan 不得引入 | **恰好一个**：DeepSeek 官方 `POST /chat/completions`（`FF-26a`）。除此之外**仍然零** |
> | 数据出境 | **零** | 仅 `FF-26d` 的**七类结构化字段**；**音频（PCM/Mel/文件）仍然零**（`FF-24` 第 8 条 = 原 `R-OUT-1` 升级为无条件约束） |
> | 权限 | 不申请 `INTERNET` | **两个风味**：`offline` 不申请（原裁定逐字节保留），`agent` 申请 |
> | 崩溃上报 / 分析埋点 / SDK 遥测 | 禁止 | **仍然禁止**。云端出口只用于用户主动发起的 Agent 对话 |
> | `R-OUT-2`（结构化记录不出网） | 无条件禁止 | **有条件放开**：仅在用户**显式同意**且**主动提问**时，按 `FF-26d` 白名单携带；`agent` 关闭态下回到无条件禁止 |
> | `R-OUT-3`（制品不得运行时从网络更新） | 禁止 | **不变，仍然禁止**。模型/知识库/SSOT **不得**热更新；云端只提供**推理**，不提供**制品** |
> | `R-OUT-1`（音频不出境） | 无条件禁止 | **不变，且升级为 `FF-24` 第 8 条**——管辖所有风味、所有版本，**不可交易** |
>
> **为什么用两个风味**：原裁定的价值不在「我们没写网络代码」，而在**一份评委可以当场 `aapt dump badging` 验证的产物**。`offline` 风味让这条主张继续拥有可执行的证据；`agent` 风味承担新定位。二者**共享同一份核心代码**。

### 1.1 原裁定的证据（历史留档，仍然成立的是它引用的 FF-24 第 5/6/7 条与 `R-OUT-1`）

| 来源 | 内容 |
|---|---|
| `SPEC-00` §3.9 **FF-24 第 4 条** | 「APK 不申请 `INTERNET` 权限」，验证方式 `aapt dump badging` —— ✅ **已由 `ADR-44` 修订为「分风味」**，见 §1 |
| 主方案 §6.1 措施 4 | 「这是最有说服力的一条……用 `aapt dump badging` 展示**这个 App 连联网权限都没有，物理上不可能上传你的声音**」—— ✅ **`offline` 风味仍然完全满足**；`agent` 风味的对应主张改为 `FF-24` 第 8 条「音频永不离开设备」 |
| 主方案 §10.2 必现图表第 7 项 | 「`aapt dump badging` 无网络权限截图 —— 隐私主张的最强证据」—— ✅ **取证对象改为 `offline` 风味的 APK** |
| 主方案 §9.2 现场 SOP | 「手机开飞行模式 → 但确保 App 不需要网络」—— ⚠️ **修订**：核心链路（检测/记录/报告/三 Demo）仍然全部离线可用（`FF-26f`）；**Agent 页**在飞行模式下显示降级态 |
| docx §10.1 | 对照表：云端模式 vs 端侧模式；本项目为端侧 —— ⚠️ **修订**：本项目为「**端侧为主、云端为可选增强**」 |

### 1.2 现行结论

> 🔴 **`agent` 风味存在且仅存在一个云端出口：DeepSeek 推理。不存在任何其他网络调用、不存在任何遥测出口、不存在音频出境路径。**
> 「拔掉网络，**核心功能**完全不受影响」现在是**可验证的不变量**（`FF-26f`），而不是「因为没有后端所以显然成立」。

因此：
1. 任何 spec/plan **不得**引入第二个云端厂商、不得引入 HTTP 客户端于 `G-01` 的 `DeepSeekClient` 之外、不得引入任何 SDK 上报 / 崩溃收集 / 分析埋点（`ADR-44` 未放开这一条）。
2. `G-*` 是**唯一**允许出现网络调用的域；`tool/check_network_boundary.py` 把这条变成机械判据（白名单目录 + 负控）。
3. §2–§8 描述的是**设备内的本地数据平面**——它**没有**因为 `ADR-44` 而改变一个字节，仍然是核心链路的全部。
4. §9 的云端同步协议 v2.0 预留设计**状态仍为 `DISABLED`**：`ADR-44` 启用的是**云端推理**，**不是**云同步。二者不可混为一谈（见 §9 开头的说明）。
5. §13（`ADR-44` 新增）是**云端推理通讯规范**，与 §9 的**云同步**协议是两件不同的事。

### 1.3 为什么仍然要写云端协议

材料中确实存在指向云端的长期目标（docx §4.3）：**AI 健康助手（LLM）**、**长期饮食趋势预测**、**健康数据融合**。这三项在设备上无法完成。
所以正确做法不是「假装不需要」，而是**现在就把接口边界定清楚**，让第二阶段可以加而不必推翻第一阶段的数据模型。**§9 的唯一目的就是让未来的接入成为"加一个实现"，而不是"改一次架构"。**

## 2. 「后端」在 v1.0 的定义

| 层 | 名称 | 运行位置 | 职责 | 权威契约 |
|---|---|---|---|---|
| **采集平面** | Native Data Plane | Kotlin 线程 | 采集 → 预处理 → Mel → 事件推送 | `API-01` |
| **持久平面** | Local Persistence Plane | Dart + SQLite 单文件 | 结构化记录、聚合查询 | `API-03` |
| **分析平面** | Analytics Plane | Dart 域层 | 评分、建议、报告、行为指标 | `API-04` |

**三者共同构成 v1.0 的「后端」**：它们提供了传统后端的三项能力——**数据接入、数据存储、数据加工**，只是全部发生在设备内且**不经过网络**。

```
        ┌──────────── 设备边界（v1.0 的一切都在这条线内）────────────┐
        │                                                              │
  麦克风 ─▶ [采集平面] ──patch──▶ [分析平面] ──▶ [表现层]
        │      Kotlin            Dart 域层        Flutter            │
        │        │                    │                                │
        │        │ 结构化字段          │ 读写                          │
        │        ▼                    ▼                                │
        │   [持久平面] ◀──────────────┘                                │
        │    SQLite 单文件（仅结构化，无 BLOB）                          │
        └──────────────────────────────────────────────────────────────┘
                    ▲                                    │
                    │ 制品导入（构建期，一次性）              │ 无任何出口
             模型/配置/知识库                            （v1.0 无数据出境）
```

## 3. 数据分类与流向矩阵

| # | 数据类 | 载体 | 是否出境 | 是否落盘 | 生命周期 | 依据 |
|---|---|---|---|---|---|---|
| 1 | **原始音频 PCM** | 内存环形缓冲 | ❌ **绝不** | ❌ **绝不** | 滚动覆盖（65536 样本 ≈ 4.096 s） | FF-24 §1 |
| 2 | **Mel 特征张量** | EventChannel 事件 | ❌ | ❌ | 消费后即可释放 | FF-24 §1 |
| 3 | **音频临时文件** | `cacheDir/audio_*` | ❌ | ⚠️ **仅当插件产生时**，须立即清除 | 启动时 + 会话结束时清理 | FF-24 §2 |
| 4 | **结构化饮食记录** | SQLite `diet_record` 表 | ⚠️ **`ADR-44` 修订**：默认 ❌；**仅** `agent` 风味 + 已同意 + 用户主动提问时，按 `FF-26d` 白名单**携带**给 DeepSeek（服务端是否留存由用户的 DeepSeek 账号条款决定，App 无法保证） | ✅ | 用户主动清除前保留 | 主方案 §6.1 §3、`FF-26d` |
| 5 | **行为指标** | SQLite `behavior_metrics` 表 | ⚠️ 同第 4 行 | ✅ | 随记录级联删除 | 同上 |
| 6 | **本地档案 / 设置** | SQLite `user_profile` 表 | ❌ **仍然禁止**（档案含目标份数等偏好，但**不含**可识别身份字段） | ✅ | 同上 | `SPEC-D-04` |
| 7 | **模型制品** | `assets/models/*.tflite` | **入境**（构建期打包） | ✅（只读） | APK 生命周期 | `API-06` |
| 8 | **知识库** | `assets/foods.json` | **入境**（构建期打包） | ✅（只读） | 同上 | `SPEC-P-08` |
| 9 | **特征配置** | `assets/feature_config.json` | **入境**（构建期打包） | ✅（只读） | 同上 | `SPEC-C-03` |
| 10 | **诊断日志** | 内存环形（最近 200 条） | ❌ | ❌（仅调试构建可落盘） | 会话内 | `API-01` §2.8 |
| 11 | **演示数据集** | 预置 JSON / assets | ❌ | ✅ | 随 App 卸载 | `SPEC-A-04` |
| 12 | 🆕 **DeepSeek API Key** | `<filesDir>/agent/credentials.json`（`0600`） | ⚠️ **出境**——但它**就是**那个出口的凭据，随 `Authorization` 头发出；**不得**出现在任何其他上下文 | ✅ | 用户清除前保留；「一键清除全部数据」**包含**它 | `FF-26b` |
| 13 | 🆕 **Agent 会话历史** | 内存（可选落盘，见 `G-02`） | ⚠️ 出境（它就是请求体本身）；内容受 `FF-26d`/`FF-26e` 约束 | ⚠️ 默认仅内存；落盘**必须**经 `U-07` 的显式开关 | 会话内 / 用户清除 | `SPEC-G-02` |

### 3.1 四条不可违反的规则（`ADR-44` 扩充为四条）

| 规则 | 内容 | 违反后果 |
|---|---|---|
| **R-OUT-1** | 类别 1、2、3 的**任何形式**（PCM / Mel / 音频文件）**永不离开进程内存**，更不出设备 | 隐私主张当场崩塌，属致命。**`ADR-44` 起升格为 `FF-24` 第 8 条，管辖所有风味与版本** |
| **R-OUT-2** | 类别 4–6 只存在于本地 SQLite 单文件；**`agent` 关闭态下没有任何导出到网络的能力**；开启态下仅按 `FF-26d` 白名单**携带**（不是"同步"、不是"上传"、不是"后台"） | 同上 |
| **R-OUT-3** | 类别 7–9 只有**入境**方向（构建期打包进 APK）；运行时**不得**从网络更新 | 引入网络依赖，破坏离线降级不变量（`FF-26f`） |
| **R-OUT-4** 🆕 | **云端出口恰好一个**：`G-01` 的 `DeepSeekClient`。任何其他文件出现网络调用即违规 | `tool/check_network_boundary.py` 会以退出码 1 拦下；这是 `ADR-44` 的兜底判据 |

> ⚠️ **R-OUT-3 的实际影响**：模型更新只能靠**发新版本 APK**，不能热更新。这是刻意接受的代价（换来「无网络权限」）。若第二阶段要做模型热更新，必须先走 §10 的启用流程。

## 4. 采集平面的通讯规范

**权威定义在 `API-01`**，本节只登记与"数据通讯"直接相关的三条：

| # | 规范 | 值 |
|---|---|---|
| 4.1 | 传输通道 | `MethodChannel`（控制，请求/响应）+ `EventChannel`（数据，单向流） |
| 4.2 | 传输格式 | `Map<String,Object?>`；批量数值用 `Float32List` / `Uint8List`，**禁 Base64、禁 `List<double>`** |
| 4.3 | 传输速率 | patch 2 次/秒 × 66 048 B = **约 132 KB/s**；level 10 次/秒 × <100 B = **约 1 KB/s** |

### 4.1 为什么不用文件交换

| 方案 | 判定 | 理由 |
|---|---|---|
| `MethodChannel` 传 `Float32List` | ✅ **采用** | 零序列化开销（`StandardMessageCodec` 原生支持）、延迟 < 1 ms、无磁盘痕迹 |
| 原生写 `.npy/.bin`，Dart 读文件 | ❌ 否决 | 引入磁盘写入 → **直接违反 R-OUT-1**；且每次 66 KB 的文件 IO 增加数十毫秒 |
| 原生写共享内存 / ashmem | ❌ 否决 | 收益（省一次拷贝）远小于实现与调试成本；10 天窗口内不值得 |
| Base64 JSON | ❌ 否决 | 体积 +33%，双侧编解码开销，且失去类型安全 |

### 4.2 背压与丢弃语义

见 `API-01` §3.3。**核心原则：丢旧不阻塞。** 实时饮食检测的语义是「当前在吃什么」，历史 patch 的丢失不会破坏结论，而阻塞原生采集线程会造成音频丢帧（`AudioRecord` 的缓冲区溢出是**不可恢复**的）。

## 5. 持久平面的通讯规范

| # | 规范 | 内容 |
|---|---|---|
| 5.1 | 存储引擎 | `sqflite`（Android 用系统 SQLite），**数据库文件名固定 `acoudiet.db`** |
| 5.2 | 进程内唯一 | 通过 Riverpod 单例持有 `Database` 句柄；**禁止多处 `openDatabase`** |
| 5.3 | 写时机 | 一次检测会话结束 → **一个事务**写入 1 行 `diet_record` + 1 行 `behavior_metrics` |
| 5.4 | 读时机 | 页面进入时按需查询，不预加载全表 |
| 5.5 | 事务边界 | 记录与行为指标**必须同事务**提交（否则会出现"有记录无指标"的脏状态） |
| 5.6 | 迁移 | `version` 单调递增；`onUpgrade` 必须**幂等且可重复执行**；升级前不得丢数据 |
| 5.7 | 加密 | v1.0 **不做**数据库加密（设备级 FBE 已提供基础保护）；如需见 §9.4 |
| 5.8 | 大小预算 | 单条记录 ≈ 300 B；一年 4 餐/天 ≈ 440 KB。**无容量压力，不做分页/归档** |

**表与字段的权威定义**：`SPEC-D-01`（数据模型）+ `API-03`（DAO 契约）+ `docs/common/docs_api/schemas/diet_record.schema.json`。

> ⚠️ **一致性红线**：`diet_record` 与 `behavior_metrics` 的关联是**强制的**。若某条记录没有对应的行为指标（例如用户手动确认的低置信度结果没有足够的咀嚼峰），必须写入一行**空指标占位**（`chewCount = null` 等），**不允许缺行**。理由：报告页的四维评分与趋势查询依赖 `LEFT JOIN` 的确定性；缺行会让"进食速度"维度的分母忽大忽小，导致评分不可复现。

## 6. 分析平面的通讯规范

| # | 服务 | 输入 | 输出 | 权威契约 |
|---|---|---|---|---|
| 6.1 | `HealthScoreService` | 时间范围 + 用户档案 | `HealthScore`（四维 + 总分 + 评级） | `API-04` §3、`SPEC-A-01` |
| 6.2 | `AdviceEngine` | `HealthScore` + 原始聚合 | `Advice[]` | `API-04` §4、`SPEC-A-02` |
| 6.3 | `ReportService` | 时间范围 | `WeeklyReport` / `TrendSeries` | `API-04` §5、`SPEC-A-03` |
| 6.4 | `FoodKnowledgeBase` | `classId` | `FoodInfo`（属性/份量/估算热量） | `API-04` §2、`SPEC-P-08` |

### 6.1 可复现性要求（**这是答辩的保命条款**）

> **同一个数据库 + 同一天 → 同一个分数。** 评分服务必须是**纯函数**（除数据库读取外无副作用、无随机、无当前时刻依赖）。
>
> - **禁止**在评分中使用"当前时间"作为判据（例如"现在是否已经过了晚饭时间"），否则同一份数据在不同时间点算出不同分数。
> - **禁止**使用随机采样或近似算法。
> - **必须**有单元测试：从当前生效数据集跑评分，断言输出**逐字段等于** UI 显示的数字（主方案 §9.1 的"共同验收方式"）。

### 6.2 单位与舍入

| 量 | 内部精度 | UI 呈现 |
|---|---|---|
| 总分 | `int`（四维各自 `round` 后求和） | `85` |
| 维度分 | `int` | `饮食规律 26/30` |
| 估算能量 | `int` kcal 区间（±20%） | `约 1100–1400 kcal` |
| 置信度 | `double` | `91%`（`round(p × 100)`） |
| 时长 | `int` 秒 | `4 分 23 秒` |

> ⚠️ **四维分数先各自取整再求和**（不是先求和再取整）。原因：UI 会展示四维明细，若先求和再取整，则 `26+24+15+17 = 82` 可能与总分 `85` 对不上 —— 这正是主方案 §3.8「已知缺口 D-1」要根治的问题。

## 7. 制品契约：AI 侧 → App 侧的离线交付

这是 v1.0 中唯一"跨系统"的数据交换，**方向是入境，介质是 Git 仓库里的文件**。

| 制品 | 源 | 目标 | 校验 | 权威契约 |
|---|---|---|---|---|
| `acoudiet_int8_v<X>.tflite` | `ai/artifacts/` | `app/assets/models/` | 体积 ≤ 2.5 MB；sha256 记录在 `model_card.json` | `SPEC-T-07` |
| `feature_config.json` | `shared/` | `app/assets/`（构建期同步） | `API-00` §3.6 握手 **15 字段**一致（`ADR-21`；原 ~~12~~） | `SPEC-C-03` |
| `foods.json` | `app/assets/` | 同上 | JSON Schema 校验通过 | `SPEC-P-08` |
| `model_card.json` | `ai/artifacts/` | 随仓库，不打包 | 字段完整（`nFrames` 必须等于 App 侧） | `SPEC-T-07` |
| `demo_dataset.json` | 团队真实累积或预置 | `app/assets/` | 与评分卡一致性测试通过 | `SPEC-A-04` |

### 7.1 交付闸门（三个 hash 必须闭环）

```
model_card.nFrames        == feature_config.n_frames     （否则张量形状不符）
model_card.melVersion     == Kotlin MelFrontend 的 melVersion（否则 ACD-CFG-001）
model_card.tfliteSha256   == sha256(app/assets/models/*.tflite)（否则制品被替换）
```

> ✅ **`nFrames = 128`**（**`ADR-21`（2026-09-12）修订**；原 `ADR-P1` 冻结值为 ~~129~~），三 hash 闭环中的 `nFrames` 一项因此可以闭合。它同时决定了模型输入形状、`model_card`、`feature_config`、Kotlin 常量四处必须一致；选项 A（128 / 4.064 s / 65024 样本）仍未采纳，理由记录在 `shared/feature_config.json` 的 `_decisions.n_frames.rejected_alternative`。
>
> ⚠️ **上例已按实际交付制品改正**（`ADR-21`）：`quantization` 由 ~~`int8`~~ 改为 `fp32`、`inputShape` 由 ~~`[1,128,129,1]`~~ 改为 `[1,128,128,1]`、`nFrames` 由 ~~`129`~~ 改为 `128`、`melVersion` 由 ~~`1.0.0`~~ 改为 `1.1.0` —— 实地安装的是 `app/assets/models/acoudiet_fp32_v1.0.0.tflite`（**4,051,716 字节**，档位 `fp32`），而**不是** int8 制品。这是"App 侧只实现 int8 那半档"（`ADR-21` 纠正的误读）在文档里留下的残迹。文件名约定见 FF-16：`<name>_<quantization>_v<version>.tflite`。

## 8. 错误、重试与一致性（本地语义）

| 场景 | 是否重试 | 语义 |
|---|---|---|
| `AudioRecord` 初始化失败（`ACD-AUD-001`） | ✅ 重试 1 次，间隔 300 ms | 设备偶发争用 |
| 设备被占用（`ACD-AUD-002`） | ❌ 不重试，提示关闭其他录音 App | 重试无意义 |
| Mel 帧数不符（`ACD-MEL-001`） | ❌ 不重试，**终止会话并上报** | 这是**契约错误**，重试只会重复失败；必须修 `P-04` |
| 模型加载失败（`ACD-INF-001`） | ✅ 重试 1 次（重新 `Interpreter`） | 罕见 IO 抖动 |
| 委托初始化失败（`ACD-INF-003`） | ✅ **自动静默回退 CPU**，不抛给 UI | NNAPI 不支持 Hardswish 是预期情况（风险 R-1） |
| 数据库写入失败（`ACD-DB-*`） | ✅ 重试 1 次；仍失败则**内存暂存 + 提示** | 绝不静默丢记录 |
| 临时文件清理失败（`ACD-IO-001`） | ❌ 不重试，只记日志 | 不阻断主流程；但**计入自检面板**并在 D9 前必须为 0 |
| 配置不匹配（`ACD-CFG-001`） | ❌ 不重试，**禁止进入检测页** | fail fast，避免"静默垃圾输出" |

**`ADR-44` 新增：云端路径的错误语义（全部被限制在 Agent 路径内，核心链路一个字不改）**

| 场景 | 重试 | 语义与用户可见表现 |
|---|---|---|
| 无网络 / DNS 失败（`ACD-AGENT-001`） | ❌ 不重试 | Agent 页显示「当前离线，核心功能可正常使用」；**不弹窗、不阻断**（`FF-26f`） |
| 未同意的用户点开 Agent 页（`ACD-AGENT-002`） | — | 显示 `C-06` 的同意门；**在同意之前一个字节都不发出** |
| 无 API Key / Key 格式非法（`ACD-AGENT-003`） | ❌ | 显示「请先在设置里填入你自己的 DeepSeek API Key」+ 入口；**不**发请求 |
| 服务端 401/403（`ACD-AGENT-004`） | ❌ | 「Key 无效或额度不足」；**不回显 Key、不写入日志** |
| 服务端 429（`ACD-AGENT-005`） | ✅ **1 次**，退避 2 s，带 `Retry-After` 则从之 | 第二次仍 429 → 告知「请求过于频繁，请稍后再试」 |
| 服务端 5xx（`ACD-AGENT-006`） | ✅ **1 次**，退避 1 s | 仍失败 → 「服务暂时不可用」，**保留用户已输入的问题**（不清空输入框） |
| 连接/读取超时（`ACD-AGENT-007`） | ✅ **1 次**（仅当尚未收到任何流式 delta） | 超时阈值见 `FF-26g`；**已收到部分内容后不重试**（否则会重复扣费并重复输出） |
| 流式响应中途断开（`ACD-AGENT-008`） | ❌ | 保留已收到的部分，标记「回复不完整」，允许用户手动重发 |
| 模型返回不可解析的工具调用（`ACD-AGENT-009`） | ✅ 1 次，把解析错误作为一条 `tool` 观察回灌 | 仍失败 → 终止本轮并如实告知；**不得**把无法解析的 JSON 当作成功结果渲染 |
| 工具调用轮次超过 `max_tool_rounds`（`ACD-AGENT-010`） | ❌ | 终止本轮，文案明说「已达到本次请求的工具调用上限」；**不得静默续跑**（`FF-26g`） |
| 用户请求调用 `FF-26i` 禁止的工具（下单/支付） | ❌ | 工具**根本不在注册表里**，模型看不到它；若模型仍产出该名字 → `ACD-AGENT-009` 路径 |

**核心链路的语义简化仍然全部成立（这是端侧优先架构的实质工程收益，答辩时值得说明）**：在 `P-*`/`D-*`/`A-*`/`M-*`/`U-01`~`U-06` 上**没有**超时、没有断线重连、没有最终一致性、没有冲突解决、没有幂等键——**全部同步语义都是"本地立即一致"**。`ADR-44` 引入的重试/超时/退避**全部**被限制在上表这一张表里，也就是 `G-*` 域内。

### 9.2 设计原则（现在冻结，将来必须遵守）

| # | 原则 | 理由 |
|---|---|---|
| D1 | **音频永不上传**，任何版本都不例外 | 差异化定位的根基；一旦上传，与 NutriEar/AudiNosh 的隐私对比消失 |

| D4 | 开启后必须**同步修改隐私主张**：移除"无 INTERNET 权限"这条宣传证据 | **这是开启云端的真实代价**（§10） |
| D5 | 客户端加密后再上传（端到端），服务端不可解密 | 降低泄露后果；代价是无法在服务端做聚合分析 |

| D7 | 删除优先（tombstone）：本地删除必须能传播到远端 | 合规要求（用户撤回权） |

### 9.3 同步信封（Envelope）草案

```json
{
  "envelopeVersion": "1.0",
  "deviceId": "<安装级 UUID，重置 App 数据后重新生成>",
  "accountId": "<v2.0 引入账号体系后的标识；v1.0 无此概念>",
  "batchId": "<UUID v4，客户端生成>",
  "sentAtMs": 1757462400000,
  "direction": "push",
  "records": [
    {
      "op": "upsert",
      "recordId": "9f1c…",
      "updatedAtMs": 1757462400000,
      "payloadJson": "<加密后的 diet_record+behavior_metrics 合并体>",
      "payloadNonce": "<12 B base64>",
      "payloadTag": "<16 B base64>"
    },
    {
      "op": "delete",
      "recordId": "3a7e…",
      "updatedAtMs": 1757462500000
    }
  ],
  "cursor": { "lastSyncedAtMs": 1757462300000, "lastServerSeq": 1043 }
}
```

- 加密：AEAD（AES-256-GCM 或 ChaCha20-Poly1305），密钥由用户口令经 KDF 派生，**不离开设备**。
- 传输：HTTPS + 双向 TLS 或 Token 鉴权（具体端点与鉴权方式**属于 v2.0 设计范围，本文不预设**）。
- 冲突解决：**`updatedAtMs` 后写胜出（Last-Write-Wins）**，但 `op=delete` 恒优先于 `op=upsert`（删除不可被覆盖）。

**机器可读版本**：`docs/common/docs_api/schemas/sync_envelope.schema.json`。

| 13.1.3 | 客户端 | `dart:io` 的 `HttpClient` + 手写 SSE 解析。**不引入 `http` / `dio` 依赖**——依赖最小化（`FF-23` 的设计选择）在此继续成立 |
| 13.1.4 | 请求头 | `Content-Type: application/json`、`Authorization: Bearer <key>`、`Accept: text/event-stream`。**不发送** `User-Agent` 以外的任何设备标识；`User-Agent` 固定为 `AcouDiet/<versionText>` |
| 13.1.5 | 流式 | `stream: true`，逐行 `data: {...}`；以 `data: [DONE]` 结束。解析器必须容忍：空行、`:` 开头的注释行、跨 TCP 分片的多字节 UTF-8、单行超长 |
| 13.1.6 | 编码 | 请求与响应一律 UTF-8。**UTF-8 解码必须跨分片缓冲**——一次 `utf8.decode` 一个 chunk 会在中文字符被切断时抛 `FormatException`（这是本项目在 `ADR-22`/`ADR-34` 都踩过的同一类坑） |
| 13.1.7 | 超时 | `FF-26g`：连接 `10000 ms`、读取 `60000 ms` |
| 13.1.8 | 重试 | 仅 §8 第二张表列出的场景，且**至多 1 次**。任何已收到流式 delta 之后**不得**重试 |

### 13.2 请求体的构造规则（**这是隐私条款的落点，不是可选的**）

| # | 规则 |
|---|---|
| 13.2.1 | 请求体是**结构化 JSON**：`model` / `messages[]` / `tools[]` / `tool_choice` / `stream` / `max_tokens` / `temperature`。**没有**任何二进制字段、**没有** base64、**没有** `Float32List` |
| 13.2.2 | `messages[]` 的内容**只能**由三类来源拼成：① 冻结的 system 提示词；② `FF-26d` 白名单的结构化字段序列化结果；③ 用户在本页**亲自键入**的文字 |
| 13.2.3 | 🚫 **禁止**把 `MelFrame`、`Float32List`、`Uint8List`、`wav` 路径、`record.audioPath` 之类的值放进任何 message。构造点只有一个（`G-02` 的 `AgentPromptBuilder`），因此这一条可以被**单点审查** |
| 13.2.4 | 单次请求体**字节数上限** `max_request_bytes = 32768`。超过 → 不放宽，改为**裁剪历史**（`FF-26g` 的 `max_history_messages`）。理由：上限存在的意义是"挡住意外把大对象塞进来"，放宽它等于删掉这道闸门 |
| 13.2.5 | system 提示词**逐字来自代码中的常量**，且必须包含 `FF-25` 的红线（不诊断、不承诺疗效、不编造数字）。**不得**由模板拼接用户数据后失去红线 |

### 13.3 响应的处置

| # | 项 | 规则 |
|---|---|---|
| 13.3.1 | `choices[0].delta.content` | 追加到界面；**不落盘**（除非用户打开会话记录开关） |
| 13.3.2 | `choices[0].delta.tool_calls[]` | 按 `index` 累积 `id` / `function.name` / `function.arguments`（**arguments 是分片的字符串，不能每片单独 `jsonDecode`** —— 这是本项目的 SSE 解析里最容易写错的一处，`G-01` 必须自带负控测试） |
| 13.3.3 | `finish_reason` | `tool_calls` → 执行工具并回灌；`stop` → 渲染终稿；`length` → 明确提示「回复被截断」 |
| 13.3.4 | `usage` | 记录到**内存**诊断（`prompt_tokens` / `completion_tokens`），供自检面板显示；**不外发、不落盘** |
| 13.3.5 | 未知字段 | **忽略**（前向兼容）。DeepSeek 的响应会加字段；因为多了字段就崩，是把"服务端升级"变成"App 崩溃" |

### 13.4 工具调用的通讯语义

| # | 项 | 规则 |
|---|---|---|
| 13.4.1 | 工具定义 | `tools[]` 由 `G-02` 的**注册表**生成，不是手写常量。**未注册的工具在模型侧不存在**——这是 `FF-26i`（禁止代下单）能成立的机制：那个工具**根本没有被定义** |
| 13.4.2 | 观察格式 | 每个工具结果回灌为一条 `role: "tool"` 消息，`content` 是**固定形状**的 JSON：`{status, summary, next_actions, artifacts}`（见 `API-07` §4）。**固定形状**是让模型能稳定解析、也让测试能逐字段断言的前提 |
| 13.4.3 | 工具失败 | `status: "error"` + `root_cause_hint` + `safe_retry` + `stop_condition`。**不允许**只回一个裸错误字符串——那会让模型重试同一个坏调用直到耗尽轮次 |
| 13.4.4 | 副作用边界 | 唯一有副作用（离开 App）的工具是 `open_takeout`，且它**只**做唤起，**不**做请求。它必须由**用户点击卡片上的按钮**触发，**不得**由模型在一次 tool_calls 里直接触发 —— 即 `open_takeout` 是一个**"提议"型工具**：模型调用它只产生一张卡片，真正执行在 UI 层 |

> **13.4.4 为什么这么设计**：如果把「唤起美团」做成模型的直接工具，那么用户的一句「我饿了」就可能让手机跳出美团——**用户没有按任何按钮**。这与"检测由用户主动发起"（`FF-24` 第 6 条）是同一条原则：**有外部可见副作用的动作必须由人按下**。
