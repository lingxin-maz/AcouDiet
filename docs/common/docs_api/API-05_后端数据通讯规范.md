# API-05 后端数据通讯规范

**上游**：主方案 §6（隐私与合规）、§9（Demo）、`SPEC-00` §3.9（FF-24）、`API-00` §1
**性质**：本文件同时是**接口规范**与**架构裁定记录（ADR）**。它回答一个必须先回答的问题：**AcouDiet 的「后端」是什么？**

---

## 1. 裁定：v1.0 没有云端后端，且不允许有

### 1.1 证据

| 来源 | 内容 |
|---|---|
| `SPEC-00` §3.9 **FF-24 第 4 条** | 「APK 不申请 `INTERNET` 权限」，验证方式 `aapt dump badging` |
| 主方案 §6.1 措施 4 | 「这是最有说服力的一条……用 `aapt dump badging` 展示**这个 App 连联网权限都没有，物理上不可能上传你的声音**」 |
| 主方案 §10.2 必现图表第 7 项 | 「`aapt dump badging` 无网络权限截图 —— 隐私主张的最强证据」 |
| 主方案 §9.2 现场 SOP | 「手机开飞行模式 → 但确保 App 不需要网络（隐私设计保证）」 |
| docx §10.1 | 对照表：云端模式 vs 端侧模式；本项目为端侧 |

### 1.2 结论

> 🔴 **v1.0 不存在任何云端后端、不存在任何网络调用、不存在任何数据出境路径。**
> 这**不是"暂时没做"**，而是**产品主张的技术基石**：评委现场看到的能力——「拔掉网络、开飞行模式，功能完全不受影响」——**只有在没有任何后端的前提下才成立**。

因此：
1. 任何 spec/plan **不得**引入 HTTP 客户端、WebSocket、SDK 上报、崩溃收集、分析埋点等任何形式的网络出口。
2. 本文档 §2–§8 描述的是 **v1.0 真正的「后端」** —— 运行在设备内的**本地数据平面**。
3. §9 给出**云端同步协议 v2.0 的预留设计**，它的状态是 **`DISABLED`：只有规范，没有实现**。

### 1.3 为什么仍然要写云端协议

材料中确实存在指向云端的长期目标（docx §4.3）：**AI 健康助手（LLM）**、**长期饮食趋势预测**、**健康数据融合**。这三项在设备上无法完成。
所以正确做法不是「假装不需要」，而是**现在就把接口边界定清楚**，让第二阶段可以加而不必推翻第一阶段的数据模型。**§9 的唯一目的就是让未来的接入成为"加一个实现"，而不是"改一次架构"。**

## 2. 「后端」在 v1.0 的定义

| 层 | 名称 | 运行位置 | 职责 | 权威契约 |
|---|---|---|---|---|
| **采集平面** | Native Data Plane | Kotlin 线程 | 采集 → 预处理 → Mel → 事件推送 | `API-01` |
| **持久平面** | Local Persistence Plane | Dart + SQLite 单文件 | 结构化记录、聚合查询 | `API-03` |
| **分析平面** | Analytics Plane | Dart 域层 | 评分、建议、报告、行为指标 | `API-04` |

**三者共同构成 v1.0 的「后端」**：它们提供了传统后端的三项能力——**数据接入、数据存储、数据加工**，只是全部发生在设备内且**不经过网络**。

```
        ┌──────────── 设备边界（v1.0 的一切都在这条线内）────────────┐
        │                                                              │
  麦克风 ─▶ [采集平面] ──patch──▶ [分析平面] ──▶ [表现层]
        │      Kotlin            Dart 域层        Flutter            │
        │        │                    │                                │
        │        │ 结构化字段          │ 读写                          │
        │        ▼                    ▼                                │
        │   [持久平面] ◀──────────────┘                                │
        │    SQLite 单文件（仅结构化，无 BLOB）                          │
        └──────────────────────────────────────────────────────────────┘
                    ▲                                    │
                    │ 制品导入（构建期，一次性）              │ 无任何出口
             模型/配置/知识库                            （v1.0 无数据出境）
```

## 3. 数据分类与流向矩阵

| # | 数据类 | 载体 | 是否出境 | 是否落盘 | 生命周期 | 依据 |
|---|---|---|---|---|---|---|
| 1 | **原始音频 PCM** | 内存环形缓冲 | ❌ **绝不** | ❌ **绝不** | 滚动覆盖（65536 样本 ≈ 4.096 s） | FF-24 §1 |
| 2 | **Mel 特征张量** | EventChannel 事件 | ❌ | ❌ | 消费后即可释放 | FF-24 §1 |
| 3 | **音频临时文件** | `cacheDir/audio_*` | ❌ | ⚠️ **仅当插件产生时**，须立即清除 | 启动时 + 会话结束时清理 | FF-24 §2 |
| 4 | **结构化饮食记录** | SQLite `diet_record` 表 | ❌ | ✅ | 用户主动清除前保留 | 主方案 §6.1 §3 |
| 5 | **行为指标** | SQLite `behavior_metrics` 表 | ❌ | ✅ | 随记录级联删除 | 同上 |
| 6 | **本地档案 / 设置** | SQLite `user_profile` 表 | ❌ | ✅ | 同上 | `SPEC-D-04` |
| 7 | **模型制品** | `assets/models/*.tflite` | **入境**（构建期打包） | ✅（只读） | APK 生命周期 | `API-06` |
| 8 | **知识库** | `assets/foods.json` | **入境**（构建期打包） | ✅（只读） | 同上 | `SPEC-P-08` |
| 9 | **特征配置** | `assets/feature_config.json` | **入境**（构建期打包） | ✅（只读） | 同上 | `SPEC-C-03` |
| 10 | **诊断日志** | 内存环形（最近 200 条） | ❌ | ❌（仅调试构建可落盘） | 会话内 | `API-01` §2.8 |
| 11 | **演示数据集** | 预置 JSON / assets | ❌ | ✅ | 随 App 卸载 | `SPEC-A-04` |

### 3.1 三条不可违反的规则

| 规则 | 内容 | 违反后果 |
|---|---|---|
| **R-OUT-1** | 类别 1、2、3 的**任何形式**（PCM / Mel / 音频文件）**永不离开进程内存**，更不出设备 | 隐私主张当场崩塌，属致命 |
| **R-OUT-2** | 类别 4–6 只存在于本地 SQLite 单文件；**没有任何导出到网络的能力** | 同上 |
| **R-OUT-3** | 类别 7–9 只有**入境**方向（构建期打包进 APK）；运行时**不得**从网络更新 | 引入网络依赖，破坏飞行模式演示 |

> ⚠️ **R-OUT-3 的实际影响**：模型更新只能靠**发新版本 APK**，不能热更新。这是刻意接受的代价（换来「无网络权限」）。若第二阶段要做模型热更新，必须先走 §10 的启用流程。

## 4. 采集平面的通讯规范

**权威定义在 `API-01`**，本节只登记与"数据通讯"直接相关的三条：

| # | 规范 | 值 |
|---|---|---|
| 4.1 | 传输通道 | `MethodChannel`（控制，请求/响应）+ `EventChannel`（数据，单向流） |
| 4.2 | 传输格式 | `Map<String,Object?>`；批量数值用 `Float32List` / `Uint8List`，**禁 Base64、禁 `List<double>`** |
| 4.3 | 传输速率 | patch 2 次/秒 × 66 048 B = **约 132 KB/s**；level 10 次/秒 × <100 B = **约 1 KB/s** |

### 4.1 为什么不用文件交换

| 方案 | 判定 | 理由 |
|---|---|---|
| `MethodChannel` 传 `Float32List` | ✅ **采用** | 零序列化开销（`StandardMessageCodec` 原生支持）、延迟 < 1 ms、无磁盘痕迹 |
| 原生写 `.npy/.bin`，Dart 读文件 | ❌ 否决 | 引入磁盘写入 → **直接违反 R-OUT-1**；且每次 66 KB 的文件 IO 增加数十毫秒 |
| 原生写共享内存 / ashmem | ❌ 否决 | 收益（省一次拷贝）远小于实现与调试成本；10 天窗口内不值得 |
| Base64 JSON | ❌ 否决 | 体积 +33%，双侧编解码开销，且失去类型安全 |

### 4.2 背压与丢弃语义

见 `API-01` §3.3。**核心原则：丢旧不阻塞。** 实时饮食检测的语义是「当前在吃什么」，历史 patch 的丢失不会破坏结论，而阻塞原生采集线程会造成音频丢帧（`AudioRecord` 的缓冲区溢出是**不可恢复**的）。

## 5. 持久平面的通讯规范

| # | 规范 | 内容 |
|---|---|---|
| 5.1 | 存储引擎 | `sqflite`（Android 用系统 SQLite），**数据库文件名固定 `acoudiet.db`** |
| 5.2 | 进程内唯一 | 通过 Riverpod 单例持有 `Database` 句柄；**禁止多处 `openDatabase`** |
| 5.3 | 写时机 | 一次检测会话结束 → **一个事务**写入 1 行 `diet_record` + 1 行 `behavior_metrics` |
| 5.4 | 读时机 | 页面进入时按需查询，不预加载全表 |
| 5.5 | 事务边界 | 记录与行为指标**必须同事务**提交（否则会出现"有记录无指标"的脏状态） |
| 5.6 | 迁移 | `version` 单调递增；`onUpgrade` 必须**幂等且可重复执行**；升级前不得丢数据 |
| 5.7 | 加密 | v1.0 **不做**数据库加密（设备级 FBE 已提供基础保护）；如需见 §9.4 |
| 5.8 | 大小预算 | 单条记录 ≈ 300 B；一年 4 餐/天 ≈ 440 KB。**无容量压力，不做分页/归档** |

**表与字段的权威定义**：`SPEC-D-01`（数据模型）+ `API-03`（DAO 契约）+ `docs/common/docs_api/schemas/diet_record.schema.json`。

> ⚠️ **一致性红线**：`diet_record` 与 `behavior_metrics` 的关联是**强制的**。若某条记录没有对应的行为指标（例如用户手动确认的低置信度结果没有足够的咀嚼峰），必须写入一行**空指标占位**（`chewCount = null` 等），**不允许缺行**。理由：报告页的四维评分与趋势查询依赖 `LEFT JOIN` 的确定性；缺行会让"进食速度"维度的分母忽大忽小，导致评分不可复现。

## 6. 分析平面的通讯规范

| # | 服务 | 输入 | 输出 | 权威契约 |
|---|---|---|---|---|
| 6.1 | `HealthScoreService` | 时间范围 + 用户档案 | `HealthScore`（四维 + 总分 + 评级） | `API-04` §3、`SPEC-A-01` |
| 6.2 | `AdviceEngine` | `HealthScore` + 原始聚合 | `Advice[]` | `API-04` §4、`SPEC-A-02` |
| 6.3 | `ReportService` | 时间范围 | `WeeklyReport` / `TrendSeries` | `API-04` §5、`SPEC-A-03` |
| 6.4 | `FoodKnowledgeBase` | `classId` | `FoodInfo`（属性/份量/估算热量） | `API-04` §2、`SPEC-P-08` |

### 6.1 可复现性要求（**这是答辩的保命条款**）

> **同一个数据库 + 同一天 → 同一个分数。** 评分服务必须是**纯函数**（除数据库读取外无副作用、无随机、无当前时刻依赖）。
>
> - **禁止**在评分中使用"当前时间"作为判据（例如"现在是否已经过了晚饭时间"），否则同一份数据在不同时间点算出不同分数。
> - **禁止**使用随机采样或近似算法。
> - **必须**有单元测试：从当前生效数据集跑评分，断言输出**逐字段等于** UI 显示的数字（主方案 §9.1 的"共同验收方式"）。

### 6.2 单位与舍入

| 量 | 内部精度 | UI 呈现 |
|---|---|---|
| 总分 | `int`（四维各自 `round` 后求和） | `85` |
| 维度分 | `int` | `饮食规律 26/30` |
| 估算能量 | `int` kcal 区间（±20%） | `约 1100–1400 kcal` |
| 置信度 | `double` | `91%`（`round(p × 100)`） |
| 时长 | `int` 秒 | `4 分 23 秒` |

> ⚠️ **四维分数先各自取整再求和**（不是先求和再取整）。原因：UI 会展示四维明细，若先求和再取整，则 `26+24+15+17 = 82` 可能与总分 `85` 对不上 —— 这正是主方案 §3.8「已知缺口 D-1」要根治的问题。

## 7. 制品契约：AI 侧 → App 侧的离线交付

这是 v1.0 中唯一"跨系统"的数据交换，**方向是入境，介质是 Git 仓库里的文件**。

| 制品 | 源 | 目标 | 校验 | 权威契约 |
|---|---|---|---|---|
| `acoudiet_int8_v<X>.tflite` | `ai/artifacts/` | `app/assets/models/` | 体积 ≤ 2.5 MB；sha256 记录在 `model_card.json` | `SPEC-T-07` |
| `feature_config.json` | `shared/` | `app/assets/`（构建期同步） | `API-00` §3.6 握手 **15 字段**一致（`ADR-21`；原 ~~12~~） | `SPEC-C-03` |
| `foods.json` | `app/assets/` | 同上 | JSON Schema 校验通过 | `SPEC-P-08` |
| `model_card.json` | `ai/artifacts/` | 随仓库，不打包 | 字段完整（`nFrames` 必须等于 App 侧） | `SPEC-T-07` |
| `demo_dataset.json` | 团队真实累积或预置 | `app/assets/` | 与评分卡一致性测试通过 | `SPEC-A-04` |

```json
// model_card.json（示例，字段权威定义见 API-06）
{
  "name": "acoudiet",
  "version": "1.0.0",
  "createdAtMs": 1757462400000,
  "quantization": "fp32",
  "inputShape": [1, 128, 128, 1],
  "numClasses": 6,
  "classLabels": ["chips","cabbage","gummies","noodles","carrot","drink"],
  "nFrames": 128,
  "melVersion": "1.1.0",
  "featureConfigSha256": "<64 hex>",
  "tfliteSha256": "<64 hex>",
  "tfliteBytes": 2411520,
  "parityLabelMatch": 1.0,
  "parityMaxConfDelta": 0.0132,
  "metricsRef": "ai/artifacts/metrics.json"
}
```

### 7.1 交付闸门（三个 hash 必须闭环）

```
model_card.nFrames        == feature_config.n_frames     （否则张量形状不符）
model_card.melVersion     == Kotlin MelFrontend 的 melVersion（否则 ACD-CFG-001）
model_card.tfliteSha256   == sha256(app/assets/models/*.tflite)（否则制品被替换）
```

> ✅ **`nFrames = 128`**（**`ADR-21`（2026-09-12）修订**；原 `ADR-P1` 冻结值为 ~~129~~），三 hash 闭环中的 `nFrames` 一项因此可以闭合。它同时决定了模型输入形状、`model_card`、`feature_config`、Kotlin 常量四处必须一致；选项 A（128 / 4.064 s / 65024 样本）仍未采纳，理由记录在 `shared/feature_config.json` 的 `_decisions.n_frames.rejected_alternative`。
>
> ⚠️ **上例已按实际交付制品改正**（`ADR-21`）：`quantization` 由 ~~`int8`~~ 改为 `fp32`、`inputShape` 由 ~~`[1,128,129,1]`~~ 改为 `[1,128,128,1]`、`nFrames` 由 ~~`129`~~ 改为 `128`、`melVersion` 由 ~~`1.0.0`~~ 改为 `1.1.0` —— 实地安装的是 `app/assets/models/acoudiet_fp32_v1.0.0.tflite`（**4,051,716 字节**，档位 `fp32`），而**不是** int8 制品。这是"App 侧只实现 int8 那半档"（`ADR-21` 纠正的误读）在文档里留下的残迹。文件名约定见 FF-16：`<name>_<quantization>_v<version>.tflite`。

## 8. 错误、重试与一致性（本地语义）

| 场景 | 是否重试 | 语义 |
|---|---|---|
| `AudioRecord` 初始化失败（`ACD-AUD-001`） | ✅ 重试 1 次，间隔 300 ms | 设备偶发争用 |
| 设备被占用（`ACD-AUD-002`） | ❌ 不重试，提示关闭其他录音 App | 重试无意义 |
| Mel 帧数不符（`ACD-MEL-001`） | ❌ 不重试，**终止会话并上报** | 这是**契约错误**，重试只会重复失败；必须修 `P-04` |
| 模型加载失败（`ACD-INF-001`） | ✅ 重试 1 次（重新 `Interpreter`） | 罕见 IO 抖动 |
| 委托初始化失败（`ACD-INF-003`） | ✅ **自动静默回退 CPU**，不抛给 UI | NNAPI 不支持 Hardswish 是预期情况（风险 R-1） |
| 数据库写入失败（`ACD-DB-*`） | ✅ 重试 1 次；仍失败则**内存暂存 + 提示** | 绝不静默丢记录 |
| 临时文件清理失败（`ACD-IO-001`） | ❌ 不重试，只记日志 | 不阻断主流程；但**计入自检面板**并在 D9 前必须为 0 |
| 配置不匹配（`ACD-CFG-001`） | ❌ 不重试，**禁止进入检测页** | fail fast，避免"静默垃圾输出" |

**无网络导致的语义简化（v1.0 的红利）**：没有超时、没有断线重连、没有最终一致性、没有冲突解决、没有幂等键。**全部同步语义都是"本地立即一致"。** 这是端侧优先架构带来的实质工程收益，值得在答辩中说明。

## 9. 预留：云端同步协议 v2.0（**状态 `DISABLED`，无实现**）

> ⚠️ **阅读须知**：本节**不是 v1.0 的工作项**。任何 PLAN 不得引用本节作为任务来源。
> 它的存在只为满足两个目的：① 让第二阶段不必推翻第一阶段的数据模型；② 在答辩中被问「未来怎么扩展」时能拿出具体设计。

### 9.1 触发条件（满足任一才启动设计）

| # | 触发 | 来源 |
|---|---|---|
| T1 | 引入 LLM 健康助手（自然语言咨询） | docx §4.3 长期目标 |
| T2 | 长期饮食趋势预测（时序模型，设备算力不足） | docx §4.3 |
| T3 | 健康数据融合（运动/睡眠/体重） | docx §4.3 |
| T4 | 跨设备同步（换手机不丢数据） | 产品自然演进 |
| T5 | 竞技/社交功能（排行榜、挑战） | 未在材料中，属推测 |

### 9.2 设计原则（现在冻结，将来必须遵守）

| # | 原则 | 理由 |
|---|---|---|
| D1 | **音频永不上传**，任何版本都不例外 | 差异化定位的根基；一旦上传，与 NutriEar/AudiNosh 的隐私对比消失 |
| D2 | 只同步**结构化记录**（类别/时间/置信度/行为指标） | 足够支撑 T1–T5，且隐私风险低一个数量级 |
| D3 | **默认关闭**，需用户显式二次确认才能开启 | 合规（PIPL/个保法）与产品信任 |
| D4 | 开启后必须**同步修改隐私主张**：移除"无 INTERNET 权限"这条宣传证据 | **这是开启云端的真实代价**（§10） |
| D5 | 客户端加密后再上传（端到端），服务端不可解密 | 降低泄露后果；代价是无法在服务端做聚合分析 |
| D6 | 同步是**增量 + 幂等**的，`recordId` 为幂等键 | 移动网络不可靠 |
| D7 | 删除优先（tombstone）：本地删除必须能传播到远端 | 合规要求（用户撤回权） |

### 9.3 同步信封（Envelope）草案

```json
{
  "envelopeVersion": "1.0",
  "deviceId": "<安装级 UUID，重置 App 数据后重新生成>",
  "accountId": "<v2.0 引入账号体系后的标识；v1.0 无此概念>",
  "batchId": "<UUID v4，客户端生成>",
  "sentAtMs": 1757462400000,
  "direction": "push",
  "records": [
    {
      "op": "upsert",
      "recordId": "9f1c…",
      "updatedAtMs": 1757462400000,
      "payloadJson": "<加密后的 diet_record+behavior_metrics 合并体>",
      "payloadNonce": "<12 B base64>",
      "payloadTag": "<16 B base64>"
    },
    {
      "op": "delete",
      "recordId": "3a7e…",
      "updatedAtMs": 1757462500000
    }
  ],
  "cursor": { "lastSyncedAtMs": 1757462300000, "lastServerSeq": 1043 }
}
```

- 加密：AEAD（AES-256-GCM 或 ChaCha20-Poly1305），密钥由用户口令经 KDF 派生，**不离开设备**。
- 传输：HTTPS + 双向 TLS 或 Token 鉴权（具体端点与鉴权方式**属于 v2.0 设计范围，本文不预设**）。
- 冲突解决：**`updatedAtMs` 后写胜出（Last-Write-Wins）**，但 `op=delete` 恒优先于 `op=upsert`（删除不可被覆盖）。

**机器可读版本**：`docs/common/docs_api/schemas/sync_envelope.schema.json`。

## 10. 启用云端的代价（**必须让决策者看到**）

若第二阶段真的要做 T1–T5，则**必然失去**以下三样东西，必须重新调整宣传口径：

| 失去的 | 影响的材料 | 替代口径（建议） |
|---|---|---|
| 「APK 连联网权限都没有」这条最强隐私证据 | 主方案 §6.1 措施 4、§10.2 PPT 第 7 项、答辩 Q&A | 改为「**音频永不上传**；只有结构化的类别与时间数据在用户显式同意后加密同步」 |
| 飞行模式下的完整功能演示 | 主方案 §9.2 现场 SOP | 核心检测链路改为「**离线可用**，云端功能为可选增强」 |
| 「无后端 = 无一致性/无重试/无冲突」的工程简化 | `API-05` §8 | 需引入同步状态机、冲突解决、退避重试 |

> 🎯 **答辩话术建议**：把「我们刻意不做云端」讲成**主动的设计选择**，而不是能力缺失 —— 「三个阶段的路线是：先证明**完全离线**可行（当前），再在**音频不出设备**的前提下叠加云端智能。顺序不能反。」

## 11. 已知缺口：数据可携带性（本方案自查发现）

| 项 | 说明 |
|---|---|
| 问题 | `X-03` 裁剪了 CSV 导出，而 v1.0 又没有任何网络出口 → **用户的数据在本机之外无法取出**。若用户卸载 App 或换机，全部历史记录丢失，且**没有任何导出途径**。 |
| 性质 | 这既是**产品缺陷**（用户资产无法迁移），也可能构成**合规瑕疵**：个人信息保护法下的「可携带权」要求提供获取与转移个人信息的途径。 |
| 影响面 | 竞赛 Demo 不受影响；但若 PPT 中强调"合规与隐私"，需注意此处不能自称"完全合规"。 |
| v1.0 建议处置 | ① 在 `U-05` 设置页**明确告知**"数据仅存于本机，卸载即丢失"；② 若余量允许，**只需一个"复制为文本"按钮**（写入剪贴板，不走网络、不走文件、约 20 行代码），即可显著缓解；③ 在 PPT「后续工作」中列出 v1.1 的 SAF 文件导出（`X-03`）。 |
| 登记位置 | 需补入 `SPEC-U-05` §10「开放问题」与 `SPEC-D-05` §9 |

> 这一条不属于"云端后端"范畴，但它是"数据通讯规范"必须交代的出口。**规范的价值一半在于写清能做什么，一半在于写清不能做什么。**
